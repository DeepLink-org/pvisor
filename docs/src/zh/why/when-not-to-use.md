# 什么时候不需要 pVisor

如果下面三条**都**成立，Agent 自带沙箱或 Docker 就够了，pVisor 这一层未必划算：

- 你只要一个用完即弃、用 `git checkout` 就能扔掉的环境；
- 不需要按路径选择性合入，也不需要"冲突时拒绝覆盖你的修改"；
- 不需要可核对的执行证据，也不需要跨 Agent、跨执行器的一致语义。

## 其他不适合的情况

| 情况 | 原因 | 建议 |
| --- | --- | --- |
| 任务的主要风险是外部副作用（调用生产 API、写数据库、发消息） | 暂存只覆盖工作区文件，不能撤销外部副作用 | 在服务端做权限与审批，或使用测试环境 |
| 需要隔离互不信任的租户 | pVisor 不是敌对多租户边界，macOS 上 VMM 仍有调用用户的宿主权限 | 使用专门的多租户沙箱或虚拟化平台 |
| 需要密码学可验证的执行证明 | 本地记录供审查和诊断，不提供远程证明 | 使用可信执行环境等方案 |
| 工具依赖 UDP、IPv6 或 QUIC，同时要求强制网络边界 | VM 数据面不支持这些协议 | 改用 host 执行并接受协作式网络边界 |
| 交互式的短任务，你本来就在旁边看着 | 审批模式的监督成本已经很低 | 直接使用 Agent 自带的审批模式 |

## 选型思路

1. 风险主要在**工作区文件**吗？是 → pVisor 的暂存与选择性合入直接适用。
2. 需要**事后说清楚**这次执行实际受了哪些限制吗？是 → 需要 pVisor 的证据模型。
3. 要在**多个 Agent 或多台机器**上用同一套语义吗？是 → pVisor 的统一入口适用；集群化仍在方向阶段，见[信任阶梯](trust-ladder.md)。

三个问题都是"否"时，更轻的方案更合适。与各方案的逐项对比见[对比](comparisons.md)。
