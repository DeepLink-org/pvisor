# 为什么是 pVisor

**限制 Agent 自主性的不是算力，而是人的监督带宽。**

## 监督成本从哪里来

今天让 Agent 做一件事，人要以下面三种方式之一付出注意力：

| 方式 | 人在做什么 | 成本随什么增长 |
| --- | --- | --- |
| 事前批准 | 逐条确认命令和文件改动 | Agent 执行的每一步 |
| 事后排查 | 通读 diff、日志，判断它有没有越界 | 每次执行的改动量和不确定性 |
| 出事收拾 | 回滚误删、轮换泄露的凭据、清理副作用 | 失败的影响范围 |

三种方式的共同点是：**每一单位 Agent 工作，都要付出差不多同等的人工注意力**。监督成本随执行量线性增长，所以无论模型多强，人能委托出去的工作量都被注意力封顶。想让一个人同时放手多个 Agent，或者让团队在流水线里无人值守地运行 Agent，都会先撞上这道墙。

## 让监督与执行量脱钩

要打破线性关系，每次执行需要同时具备三种性质，各自消除一类监督成本：

| 性质 | 含义 | 消除的监督成本 |
| --- | --- | --- |
| 有界 | 出错的影响范围事先可知 | 不必逐条事前批准：最坏情况已经被边界限定 |
| 可逆 | 暂存文件可选择性合入、丢弃或分叉 | 降低出事收拾的成本：失败的结果可以整体扔掉 |
| 可查 | 执行留下可核对的证据 | 事后排查可以抽样，最终交给机器判定 |

缺一不可：只有边界没有证据，人仍要通读结果才放心；只有证据没有可逆，发现问题时已经来不及；只有可逆没有边界，暂存之外的副作用仍然无人约束。

## pVisor 的定位

pVisor 是让每次 Agent 执行具备这三种性质的**执行层**：

- 它不是又一个沙箱：边界之外，它还提供暂存与选择性合入，以及一份说明"实际生效了哪些限制"的证据；
- 它不是调度器：它定义一次执行的语义，可以运行在 host、容器或 VM 上，未来与 Kubernetes、Ray 等调度器配合，而不是替代它们；
- 它不绑定某个 Agent：Claude Code、Codex 或任意脚本都使用同一个入口和同一套语义。

委托的规模因此由策略和证据决定，而不是由人盯着的时间决定。

## 今天与方向

今天 pVisor 交付的是第一级：在本机让一个 Agent 全自动跑完，事后审查每个改动并选择性合入。更高的级别（由策略和证据决定哪些改动免审、多个 Agent 并行、集群化执行）建立在同样的三种性质上，分级与规模轴见[信任阶梯](trust-ladder.md)。

衡量这条路线的指标是**每单位 Agent 工作所需的人工监督成本**：人工介入的次数和花费的时间。度量方法与实测计划见[监督成本（规划中）](../benchmarks/supervision-cost.md)。
