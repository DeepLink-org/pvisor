# 核心设计原则

pVisor 的设计围绕三个问题展开：如何约束 Agent 的执行，如何管理执行过程中的状态与资源，以及如何确认执行结果。以下原则说明这些设计的依据与必须保留的边界；组件分工和运行流程见[架构总览](index.md)。

<a id="_2"></a>

## 共享契约与执行实现分离 {#separate-definitions-from-execution}

不同接入方式和执行器应共享一致的操作、策略与结果语义，具体平台机制由各自实现承担。core 定义共享契约，pVisor Runtime 与驱动负责落实执行。例如，Host 与 VM 执行器使用共享的操作与结果契约，但分别通过宿主进程和 guest 执行工具，支持的控制能力也可以不同。契约随实际接入需求扩展，避免提前抽象尚无调用方的能力。组件分工见[核心架构](architecture.md)。

<a id="_6"></a>

## 控制保证以实际执行边界为准 {#guarantees-require-actual-boundaries}

声明策略表达约束要求，能够提供的保证取决于实际安装的控制及其覆盖的访问路径。例如，VM 的网络出口由 OverlayNet 检查访问规则，而普通 TLS 连接中的模型消息只有通过 Gateway 接入时才进入相应的模型观察路径。策略被接受或访问被记录，都不能单独证明约束已经生效。能力说明必须以执行器和平台的实际控制边界为准，见[能力与证据](../concepts/capabilities-and-evidence.md)及[隔离设计](isolation.md)。

<a id="_5"></a>

## 执行收尾与终态由统一责任方管理 {#one-lifecycle-owner}

一次执行无论正常结束、被取消还是中途失败，都应由明确的责任方完成资源清理并公布终态，避免多个组件各自认定任务已经结束。Session 统一管理 Attempt 的生命周期，驱动报告输出与观察。例如，工具进程退出后，仍需完成资源清理和必要的结果保存，才能公布任务终态。取消是停止请求，不等于任务已经完成；执行失败与记录失败也应分别报告。收尾流程见[执行模型](execution-model.md#attempt-completion)。

## 资源驻留与执行需求相匹配 {#resource-lifecycle}

保留 Agent 的执行上下文，不意味着始终保留全部驻留资源。共享与按需加载减少重复保存和提前准备的成本，生命周期管理决定何时保留或回收资源。例如，在受支持的模型等待路径上，Host 继续等待响应，并结合 guest 空闲证据管理 VM 的暂停、内存卸载与恢复。回收必须满足执行与设备访问的安全条件，并权衡等待长度和恢复代价，不能只追求更低的驻留内存。具体机制见[沙箱生命周期管理](../concepts/lifecycle.md)和[镜像与内存优化](../concepts/resource-optimization.md)。

<a id="_7"></a>

## 执行改动与结果接受分离 {#review-files-before-applying-them}

执行成功不意味着所有文件改动都应该被接受，失败执行也可能留下有用的改动。启用暂存后，候选改动独立保留，供调用方审查并选择接受。例如，Agent 对 `config.toml` 的修改先保留在私有 upper 中，调用方查看 diff 后，通过 Apply 将选定改动写入目标工作区。这一机制约束暂存范围内的文件变化，不能撤销已经发生的外部副作用。操作关系与适用范围见[文件级监管与隔离](../concepts/staging.md)。

## 记录区分意图、决定与事实 {#separate-requests-decisions-and-facts}

记录应关联执行意图、实际决定与观察结果，同时保留它们各自的含义，不能以其中一类替代另一类。请求被改写时同时保存原始与有效快照，避免最终决定覆盖原始意图。例如，“请求访问某个域名”“策略允许该访问”和“实际连接成功”是不同的信息，不能用授权决定代替运行结果。各类信息及其关联对象如下：

记录使执行过程可审查，但 Event 本身不足以确定性重放副作用。记录语义见[Operation 与 Event](operations-events.md)，回放所需的状态、输入与执行机制见[回放设计](replay.md)。

<a id="_4"></a>

## 保留执行中的因果依赖 {#preserve-known-causal-dependencies}

Agent 的后续操作可能依赖前一步的输出，调度、转发和执行必须保留这种已知依赖，不能因执行位置或并发方式变化而破坏先后关系。例如，Agent 先修改配置再运行依赖该配置的测试，测试必须读取修改后的状态，不能因并发调度而提前执行。记录应保留相应的因果引用；Journal 提交顺序与观察时间不能代替因果关系，也不能据此推断跨 Job 的全局副作用顺序。记录字段与顺序语义见[Operation 与 Event](operations-events.md)和[Journal 设计](journal.md)。
