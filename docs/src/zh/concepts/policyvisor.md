# PolicyVisor 的设计思路

**策略约束下的可审查执行。**

PolicyVisor 简称 **pVisor**，管理 Agent CLI、脚本和自动化命令的执行。**p 代表 Policy**：一次 Run 的权限与约束、落实这些约束的运行时机制，以及可供审查的证据。

原有命令仍然负责具体任务。PolicyVisor 管理它的执行过程，不依赖特定推理框架或业务逻辑。

## 从策略到可审查的结果

1. **声明权限。** 为任务选择执行器、工作区和能力要求。需要先审查文件改动再写入项目时，显式启用 `--stage`。
2. **检查能力。** 准入过程根据所选 provider 评估能力要求。必要的控制必须得到支持，可选控制的降级必须在运行记录中可见。
3. **执行控制。** 宿主机、容器或 VM 执行器及其运行时组件提供实际边界。网络策略约束这些机制能够中介的流量。
4. **审查证据。** 在 Run Bundle 中查看结果、实际安装的控制、警告和观察到的 Effect，再选择应用暂存文件或丢弃剩余改动。

这里的策略指 Run 的能力要求与运行时配置，不意味着引入了新的策略语言、中心化策略服务，或所有平台都具备相同的强制执行能力。

## pVisor 当前实现

pVisor 将 Run 身份、宿主机／容器／VM 执行器、能力准入、OverlayFS 暂存、可选的 Gateway 捕获、网络策略和本地执行记录组合起来。用户入口是[运行、审查与应用](../start/first-run.md)。模型捕获、协作式 AgentCtl 等 Agent 专用集成按需扩展这个流程。

声明的权限、实际控制和观察到的结果是不同的事实。显式代理控制配置过的客户端流量，本身不能阻断直接 socket。文件系统检查点保存暂存文件，不保存进程内存。应用或丢弃暂存文件也无法撤销远程 API 调用。

## 后续设计方向

集群部署、可验证的节点证明、跨服务的效果事务，以及面向恶意租户的隔离，属于后续设计方向，不是当前本地 CLI 的保证。详见[路线图](../development/roadmap.md)和[从本地到集群](../design/local-to-fleet.md)。

评估一次运行的边界时，应查看具体的[能力证据](capabilities-and-evidence.md)。
