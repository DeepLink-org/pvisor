# Cluster benchmark 应先回答的问题

benchmark 应按“产品决策 → 可证伪假设 → 对照与控制变量 → 测量 → 判断”组织。画出内存和启动时间曲线本身，不足以证明 pVisor 的扩展性或商业优势。

默认研究场景是固定宿主预算下的 Agent 执行：短工具计算与长模型等待交替，多个任务共享资源，Controller 重启后通过 Worker 对账。这个场景是研发假设，还不是经过客户验证的需求。

后续方向补充：优先验证[共享工作集与惰性加载](../design/cluster/shared-working-set.md)的 S1–S5。重点是假设“共同基底按组支付一次，任务按实际访问与私有修改支付增量”，同时测首次有用结果与任务完成。普通独立启动探针没有覆盖这些机制；缓存命中与较低 ready延迟不能直接代替固定预算有效工作收益。

本协议在[2026-10-05 探索性测量](cluster-scalability.md)之后编写。**下面的问题没有在那批数据采集前注册，不能追认那批测量已经验证了它们**。本页用于设计下一轮实验；没有新增 VM 实测或新的 PASS。

## 现有曲线回答了多少 {#existing}

| 已有观测 | 能回答的问题 | 不能推出的结论 |
|---|---|---|
| 1→4 台，内存 93→343 MiB | 在最小 shell/sleep 负载下，增加一台 VM 和一个 Worker 的平台期资源增长是否异常？未观察到明显超线性增长 | 真实 Agent 的边际内存、单 Worker 密度、启动峰值、长时间泄漏或固定 RAM 下容量 |
| 就绪 P50 3.81→4.38 s；启动速率 3.45 倍 | 增加 Worker 且增加 CPU 预算后，这批轻量任务能否并行就绪？可以 | 固定机器下的任务完成吞吐、优于其他运行时、调度开销小；86.2% 是该探针的启动效率比，不是产品整体扩展效率 |
| 计数约 129–287 ns，百万历史全扫描参考约 134 ms | 增量计数索引是否避免历史全表扫描？本测量与此机制一致 | Controller HTTP 吞吐或百万活跃任务的调度能力 |
| 百万记录约 6.39 GiB RSS、热回放 16.09 s | 长期历史保留是否可能形成内存与恢复负担？是，值得进一步定位 | 净 Controller 内存、冷恢复 SLO或具体压缩方案的收益；RSS 含 fixture，只有单次回放观察 |

因此，原曲线应保留为探索与定位证据，不作为固定预算高密度、生产容量或竞品优势的验证。3.8 s 的就绪时间需要分解，现有数据没有测各阶段，也不能与不同配置下的纯 VM 启动直接相减。

## Q1：启动等待主要花在哪里？ {#q1}

**决策：先优化 Controller、Worker 准备、VM，还是先处理 CPU 配额？**

假设：Cluster 在同等原生配置下增加的排队/控制/准备成本显著，足以解释用户可见启动等待的一部分。

对照为直接原生 VM 执行与经 Cluster 执行。两者使用同一冻结 release 制品、rootfs、firmware、策略、guest CPU/RAM、host cgroup 和就绪标记；先测并发 1，再测 2、4。冷准备与已准备环境分开；CPU 配额作为另一个独立实验因素。不能拿现有 debug/0.5 核数据和历史另一种配置的数据比较。

记录每个任务的提交、意图提交完成、assignment 发出/接收、Worker 准备结束、原生 VM 启动、guest-ready，以及 cgroup CPU usage/throttled、排队长度和失败。跨进程/主机阶段要说明时钟误差；未来跨主机不能直接相减未校准时间戳。提交到就绪总时延与完整任务完成时延分别报告。

判定看成对差值和阶段分布：若主要成本在原生准备，优化 Controller 无法解决主问题；若调度队列随并发增长，而直接执行没有相同增长，优先处理控制/调度路径。没有对照、时钟质量不足或差异落在波动范围内，结果为未定位，不作因果结论。

## Q2：每多一个 Agent，要多付出多少真实内存？ {#q2}

**决策：节点容量如何预算，内存优化应投向 VMM/guest、工作区共享还是 offload？**

假设：公共环境能摊薄共享开销，offload 能降低等待期物理占用；两者的恢复代价不会抵消收益。

固定环境与每任务输入，分别测空闲 guest、真实工具任务及带校验的固定私有工作集。并发 1、2、4；把单 Worker 多 guest 与多 Worker 部署分开。保持 Controller/Worker 基础成本可单独采样。可逆地比较普通驻留、同样状态的暂停，以及 offload；状态、CPU 预算和 guest RAM 不变。

报告基础服务内存、平台期/启动峰值、每个 native PID 的身份与 PSS、cgroup anon/file/shmem、配置 RAM与实际工作集，另报 offload 存储写入量、恢复/首次读取时延和数据校验。`file` 不能直接当成可回收缓存扣除；宿主 cgroup、PSS 和逻辑 reservation 不混用。

判定用边际成本与内存占用随时间的积分，并同时看恢复任务的完成时延、CPU和 I/O。仅降低一个 RAM 代理或平台期数值不能判定总体收益。当前 offload 不释放逻辑 RAM reservation/槽位，所以物理占用降低不能直接宣称准入容量提升。

## Q3：固定 CPU/RAM 预算，能多完成多少正确的 Agent 工作？ {#q3}

**决策：模型等待时释放 CPU 是否值得默认启用，是否形成可售卖的单位成本优势？**

假设：长模型等待、短工具计算的负载中，暂停并释放逻辑 CPU 可以提高有效完成吞吐；CPU 密集负载应提供负对照，不能假设同样获益。

冻结宿主总 CPU/RAM 上限、任务集和 arrival trace。同一实现比较普通执行与 `release_cpu_on_idle`，在 CPU 密集、模型等待为主、交替工具/模型三种负载分别测试。模型端返回确定内容与固定延迟，工具实际执行并校验产物；不要通过改变输出、模型延迟或计算量制造增益。

每组至多四个真实 guest，积压任务可多于四个但必须排队。可按一个 Worker 的四槽位、两核预算和每任务一核逻辑预留设计：普通路径至多两个计算任务，等待释放 CPU 后能否准入其他任务就是被测问题；RAM/槽位上限始终有效。单 Worker 与四个独立 Worker 的效果不能混为一谈。

主要指标是**单位时间正确完成的任务数、固定输入的完成时延、CPU 秒/成功任务、物理内存占用随时间的积分/成功任务**，另报提供方等待、VM存活数、CPU预留与实际使用率。把暖启动、证据上传、Controller、Gateway、模型服务是否计入成本写清；失败、超时、未完成任务不能从分母中消失。

判定是相同工作与预算下的成对收益，而非 VM 数或启动速率。收益若由增加 CPU预算、减少工作或忽略交付造成，则假设没有得到支持；CPU不足、尾延迟恶化和更高驻留内存均可能抵消吞吐收益。多台暂停 VM说明调度机制发生变化，不自动说明客户任务更快或成本更低。

预先定义 `R = throughput_idle / throughput_ordinary`，其原假设为 `R ≤ 1`。正式协议需在 pilot 后、正式采样前冻结有实际意义的最小收益、批次级成对置信区间方法和允许的时延/内存代价。区间跨过 1 则证据不足；仅 `R > 1` 的点估计不能宣称有效优势。即使吞吐假设成立，是否值得默认开启仍要结合成本与客户约束决策。

## Q4：历史任务会不会拖慢当前调度？ {#q4}

**决策：继续优化 ready/poll 热路径，还是优先压缩历史与优化管理接口？**

假设：固定活跃集合时，热 poll 的候选处理工作量不随终态历史线性增长；大量 ready 候选、能力不匹配或管理查询仍可能影响尾延迟与公平性。

先固定 Worker 数、active/ready 集合和提交速率，只增加终态历史。再固定历史，分别改变 ready 集合、Worker 数和不匹配候选比例。同时测 typed API 与真实 HTTP；协议模拟 Worker 不等于真实部署 Worker，更不等于 VM 并发。

报告提交→分配 P50/P95、poll 时延/CPU/候选访问数、排队最长时间、控制服务 RSS与分配器/fixture 开销，以及低频意图/回执日志写入、压缩/回放成本。`queue_lookahead` 对候选访问的限制是局部机制断言，不承诺整个请求为常数时间。

判定应能区分“历史导致热路径扫描”“活跃集导致工作增加”和“内存/日志保留成本”。计数纳秒级不能替代这些测量。百万历史的既有结果保留，但下一轮受限实验只取预算内规模，不能为了凑曲线重跑超过预算的点。

## Q5：最终一致对账能否在重启后安全收敛？ {#q5}

**决策：简化后的 Controller 是否保留执行语义，恢复成本是否可接受？**

假设：Worker 可达时，重启后能在不改写执行身份、不重启同一 native 执行的条件下恢复调度；Worker 不可达时，保持 pending 与资源预留。

在最多四个运行/暂停/待交付 guest 下重启 Controller，分别让 Worker 正常、延迟上报或暂时失联。分开记录进程启动、日志回放、HTTP健康、首个正确状态、可达 Worker 的对账覆盖率、全部可达身份确认以及恢复新任务准入的时间。

同时核查完整 lease key/generation、fixture 中执行启动计数、资源/证据引用、取消/控制交付。失联 Worker 不自动宣告恢复完毕；不得因旧 deadline 自动释放资源或重派未知执行。永久分区的收敛时间是未定义，而不是零或超时后的成功。

判定先过安全断言，再评价恢复时延。局部一次 fixture 没有重复执行，不证明任意外部系统的 exactly-once；本地日志热回放也不是最终一致状态完整收敛时间。完整坏日志等预期拒绝必须与运行性能故障分开报告。

## Q6：持续运行后，资源和延迟会不会累积？ {#q6}

**决策：当前实现是否适合常驻 Worker，产物/历史保留的容量策略是否足够？**

假设：在有界历史/证据策略下，任务重复创建、结束、取消和交付后，活跃进程、fd、挂载与运行资源预留不会持续累积。

用固定输入重复执行，最多四台同时存在。固定保留策略，测早期/中期/后期批次与 GC 前后；区分保留证据、保留任务元数据、可回收页缓存和原生资源。若终态记录有意保留，不能把历史增长全部称作泄漏。

报告 native 存活身份、fd/挂载数、运行 reservation、服务内存、文件/日志字节、启动和完成时延随累计任务量变化。取消/失联样本单独标记，不能通过跳过异常路径让曲线变平。

判定资源是否按生命周期与明确保留政策收敛。若没有实现有界终态保留，则长期容量假设尚不能验证，即使 42 次启动都成功也不能给出长期稳定性 PASS。

## 测量前必须冻结的协议 {#protocol}

每轮保存问题 ID、欲影响的产品决策、假设/反例、对照版本与完整配置、主指标公式、次指标、正确性断言、负载/到达轨迹/随机种子、资源上限、样本数与停止规则、失败计数方式和结果判定。冻结后改变配置或指标要建新协议并说明原因；探索结果不能事后标成预注册验证。

本页是问题与协议草案，尚未冻结正式负载、样本数、统计方法和业务门槛，**不是可直接执行并打分的验收协议**。每个正式实验记录“支持、否定或未决”；安全断言失败独立记录为失败，不能用性能收益抵消。预算内没有测到的点与统计证据不足均属于未决。

使用冻结 release 二进制与源码/firmware/rootfs身份，A/B 顺序交替或随机化，先做小规模 pilot 估计波动再冻结正式样本数；pilot 不计入正式结果。按批次保留原始数据，对成对差异与波动分别报告，不能把同批任务当作独立宿主重复。客户尚未给出绝对延迟/恢复 SLO；研发筛选目标应在正式采样前声明，不从结果反推门槛。

全部实验延续最多四个真实沙箱、每沙箱明确 guest RAM/vCPU/CPU时间限制，以及 host 内核 CPU/内存上限、禁用 swap 和可用内存预检。总预算不得随 A/B 变化。单 Worker 多 guest 需要另外验证每 guest 限制与全树限制；不具备所需限制时标记未测。对照运行顺序执行，不为 A/B 同时开八台。

合成 Controller/Worker 协议负载也必须限制 CPU/RAM，记录模拟身份；更大记录集合或沙箱规模不自动获得资源授权。接近预算时按事先声明规则停止并记录未测/失败，而不是通过弱化工作负载或跳过结果获得 PASS。

## 执行优先级与竞争结论 {#priority}

先做[共享 RAM 与环境 lazy路径 S1/S2](../design/cluster/shared-working-set.md#experiments)，与 **Q1 启动归因 / Q2边际内存**结合；S3解释并发miss成本，然后在 **Q3 固定预算有效工作吞吐**中验证组合收益。Q4/Q5用于检验控制面设计，Q6检验长期容量假设。已有能力、待建对照harness和后续架构提案分别标明，先冻结协议再执行。

对 Firecracker 等运行时的下一步比较应使用相同工具/输入/任务到达与总预算，并单列隔离边界、发行版准备/镜像成本和生命周期能力。无法匹配时按部署场景分别报告。对 Agent Env 等产品也先确定客户任务与语义，不把普通 microVM 的启动、平台 SLA 和 Agent 完成吞吐放进同一排名。没有同协议实测前，不能给出竞品性能胜出结论。
