# 选本机 pVisor，还是 E2B、Daytona、Modal？

## 主要结论 {#conclusions}

**pVisor 适合直接使用本机仓库与工具链；E2B、Daytona、Modal 适合需要远端环境供应和托管容量的场景。** 没有同条件云端延迟或账单数据，无法声称 pVisor 更快或更便宜。

本机已准备环境的 pVisor VM 启动约 **0.1 s**，staged 的短修复任务约 **0.7 s**。搬到远端时还要计入上传、环境准备、执行和结果回传，不能只比较环境创建时间。

| 需求 | 选型含义 |
|---|---|
| 已有本机仓库和工具 | 评估 pVisor 的本地反馈预算 |
| 需要远端环境与托管容量 | 评估 E2B、Daytona、Modal |
| 比较成本或速度 | 需要同区域端到端任务实测 |

## Motivation {#motivation}

选择本地或云端不仅取决于启动。仓库位置、已有工具、弹性容量、结果回到工作区的流程都会改变端到端成本。

## 实验设计 {#interpretation}

本页比较部署方式；性能证据仅来自本机测量，未创建云端 sandbox。云端 SDK、区域、账户、缓存、延迟和账单未测。官方资料只用于说明环境供应方式，不采用宣传值排序。

| 方案 | 执行与准备方式 | 用户需要承担的流程 |
|---|---|---|
| pVisor 本地 | 本机目录或准备好的 rootfs，stage/apply | 本机资源、依赖与运维 |
| E2B | SDK 操作远端 sandbox、准备模板与文件 | 模板、输入上传、结果回传与本地合入 |
| Daytona | SDK 管理远端开发 sandbox | 环境准备、同步和结果合入 |
| Modal | SDK 创建 sandbox，使用镜像和存储 | 依赖镜像、数据接入与流水线连接 |

官方说明：[E2B](https://docs.e2b.dev/)、[Daytona](https://www.daytona.io/docs/en/)、[Modal Sandboxes](https://modal.com/docs/guide/sandboxes)。

固定制品与测量日期按表注明。失败与校验不通过的样本不计入成功耗时，失败数量单列；既有数据没有事先的宿主干扰剔除规则，所有通过校验的慢样本保留。30 次及更少采样的 P95 仅为观察参考，不给 P99 或稳定尾延迟承诺。

## 实验数据和分析 {#results}

本地数据见[启动](startup.md)、[任务](agent-tasks.md)和[密度](density.md)。它们可估算本机短任务预算，不代表托管服务的容量或可用性。

比较同一任务应完整记录环境构建、上传、创建、依赖缓存、执行、下载与合入。长期复用环境时，准备成本会摊薄；频繁上传大仓库则可能扩大远端等待。云端快照或暂停恢复也不自动完成本地目录的冲突合入。

成本应包含资源时间、存储/网络、套餐与模型费用；本地还要包括硬件和运维。没有账单实验，因此只提供选型条件：需要远端 API 和突发容量时评估托管服务；已有本机依赖和短反馈回路时评估 pVisor。
