# 多个 VM 如何节省内存？

## 主要结论 {#conclusions}

Agent 在工具执行期间加载依赖、读取文件和处理数据，多个环境可能在相近时间使用相同内容。**pVisor 通过尽早共享重复页面，并在后续读取时保持共享，减少这些执行环境同时驻留的内存。**

- **让共享尽早生效。** 相同随机内容的预检中，物理池约 1.7 秒达到持续减少 128 MiB 的观测目标，为短时工作集提供了早期回收的依据。
- **把共享延续到下一次读取。** 物理页共享在读回后保持低占用；显式不可变文件还可通过 DAX 直接复用，文件读取提示帮助扫描器更早发现候选页。
- **结合工作集评估整体成本。** 共享收益取决于重复程度和页面存活时间，需要同时考察扫描 CPU、观察窗末尾占用，以及压缩路径恢复私有 RAM 的代价。

## 实验动机 {#motivation}

Agent 的读文件、搜索和小脚本调用可以很短。对于短命工具环境，或者很快被释放、改写的工作集，即使几十秒后的内存占用很低，也可能赶不上实际可共享的窗口；因此要同时看曲线前几秒和窗口末尾。持久 VM 的库页可能跨多次调用保留，工具执行时间不能直接当作页面可共享时间。部署时应按工作集生命周期，权衡回收速度、扫描 CPU、读回开销和完整运行组的内存预算。

## 实验设计 {#interpretation}

评估去重应分别使用易压缩的重复内容、跨实例相同随机内容和各实例独有随机内容，在相同观察窗口下比较空闲占用、回收速度、CPU 和首次完整读回。共享库单独比较普通文件加载、文件读取提示和显式不可变 DAX，避免把不同负载混成一个排名。

当前工程预检每组四实例，各有 64 MiB 数据；VM 为 256 MiB RAM／1 vCPU，Docker 每容器限制为 256 MiB／一核配额。完整组统一四核／2 GiB／零 swap，包含共享池或专用 rootless Docker 运行时。就绪后观察 60 秒，每条件 N=1，内容、私有写入、退出和资源校验均须通过；失败与不完整批次不参与汇总。具体环境和采样边界见[工程实验设计](../../design/vm-memory-performance-analysis.md#pool-design)。

这是同预算、同负载的完整配置对照。Docker 使用专属 rootless daemon，运行时成本由四容器承担；共用 daemon 的部署可有不同的摊销结果。Firecracker 与 pVisor 的客户机内核、virtio-blk／virtio-fs 文件路径不同，Docker 共享宿主内核。全局 ksmd 在组 CPU 配额外单列，因此这些结果不能全部归因于扫描算法。

**cgroup 计费内存**包含归属于组的缓存和内核开销；**PSS**按比例分摊进程映射的共享页。文件页可能计费在组外，因此两个指标分别保留，不能相加，也不能直接换算整机新增占用。重复轮次、真实 Agent 延迟与长期容量仍未测。

### 整组总量与每 VM 平均值 {#memory-accounting}

**图中显示四实例整组总量，尚未除以 VM 数量。** daemon 方式包含 `pvisor-daemon memory-pool` 进程、全部 VM 进程和组内辅助进程。换算每 VM 的平均占用时：

- **平均进程 PSS** =（内存池进程 PSS + 全部 VM 进程 PSS + 组内辅助进程 PSS）÷ 4。PSS 按映射比例分摊共享页；直接相加 RSS 会重复计算共享页。
- **平均组计费内存** = 完整 cgroup 的 `memory.current` ÷ 4。这个读数已经包含内存池，以及归属于组的文件缓存和内核开销，无需另加 daemon 内存。

这里的平均值是整组成本的分摊，不代表新增一个 VM 的边际成本。实验启动的是独立内存池组件，没有启动完整 OpenSandbox API 服务；组外观察者也不计入上述内存。

### 如何区分去重与压缩 {#dedup-modes}

物理页共享在读取时继续复用同一份数据；冷压缩在访问时恢复私有内存。评估收益需要同时看空闲占用、回收速度、扫描 CPU 和首次读回后的占用。

| 实验标签 | 内存处理方式 | 跨 VM 复用 | 重新读取时 |
|---|---|---|---|
| `off` | 关闭额外 RAM 去重和冷压缩 | 不主动合并 RAM | 读取原有页面 |
| `ksm` | 宿主内核扫描并合并相同页 | 内核持有共享页 | 保持共享，写入时复制 |
| `local` | 每实例独立压缩冷块，可在本地池内去重 | 不跨 VM 共享压缩对象 | 恢复为本实例私有 RAM |
| `physical` | daemon 持有相同内容的共享物理页 | 多 VM 映射同一份页 | 保持共享，写入时复制 |
| `compressed` | daemon 保存可复用的压缩冷块 | 多 VM 复用压缩对象 | 恢复为本实例私有 RAM |

当前物理共享按 4 KiB 页处理；本地压缩和公共压缩池主要按 64 KiB 块处理，并要求达到压缩收益门槛。因此，跨 VM 完全相同但难以压缩的数据，仍可能被压缩路径拒绝。模式标签用于工程对照，不代表可直接叠加的配置选项。

不可变文件的 DAX 共享是另一条路径：各 VM 直接映射同一底层文件的相同偏移，无需先扫描这些文件页。当前共享库实验使用显式不可变挂载；普通 rootfs 的所有 `.so` 不会自动获得这一属性。普通文件读取提示只调整物理池候选页的扫描顺序，合并前仍需验证内容。

![三种工作集的 60 秒内存曲线：Firecracker、Docker 与 pVisor](../../assets/benchmarks/memory-pool-static-idle.svg)

图中每行依次为重复内容、跨实例相同随机内容、各实例独有随机内容；左列是整组 cgroup 计费内存，右列是进程 PSS。横轴为全部实例就绪后的秒数，纵轴为 MiB，每条件 N=1。物理池在相同随机内容上较早下降，KSM 在观察窗末尾占用更低；独有随机内容则显示共享收益有限。

### 回收速度与 CPU 成本 {#reclaim-cost}

下表对应跨实例相同随机内容：每条件 N=1，内存为四实例整组在 60 秒时的计费 MiB，CPU 为 60 秒窗口累计 CPU 秒。回收时间从各自全部就绪的计费占用开始，记录持续减少 128 MiB、并保持至观察窗结束的采样区间；“未达到”表示窗口内未达到此目标。

| 模式 | 60 秒计费 MiB | 组 CPU 秒 | 持续减少 128 MiB 的时间，秒 |
|---|---:|---:|---:|
| firecracker | 365.67 | 0.164 | 未达到 |
| docker-rootless | 423.99 | 0.183 | 未达到 |
| pvisor-off | 398.91 | 0.386 | 未达到 |
| pvisor-ksm | 177.33 | 0.384 | 27.723–27.773 |
| pvisor-physical | 222.61 | 5.924 | 1.688–1.739 |
| pvisor-compressed | 377.89 | 2.838 | 未达到 |
| pvisor-local | 373.48 | 2.341 | 未达到 |

KSM 另有 **0.41 CPU 秒**全局 ksmd 开销，位于组配额外，不能完全归因到本组。组 CPU 包含 VM、内存池和组内控制工作；这些读数衡量完整路径成本。

这组曲线呈现了回收速度与持续成本的取舍：物理池约 1.7 秒达到观测目标，KSM 约 27.8 秒达到该目标，并在 60 秒时取得更低的占用和 CPU 读数。短时工作集更关注前几秒已经释放的内存；长期保留的页面则有更长时间积累共享收益。具体选择取决于页面可共享寿命和 CPU 预算。

这里没有测量真实 Agent 调用时长分布，也未证明亚秒级调用的收益。达到目标的时间不代表首次合并或完整收敛；持久 VM 中的页面可以跨多次工具调用继续共享。

### 读回后还省内存吗？ {#readback-cost}

以下另取重复内容负载，每条件 N=1；内存为四实例整组计费 MiB。完整读回耗时包含四实例的数据读取、逐字节与摘要校验及控制传输。

| 模式 | 读回前 MiB | 读回后 MiB | 完整读回 ms |
|---|---:|---:|---:|
| pvisor-off | 398.92 | 399.09 | 621.99 |
| pvisor-local | 117.46 | 374.58 | 1157.44 |
| pvisor-compressed | 186.17 | 419.73 | 1099.13 |
| pvisor-physical | 149.14 | 149.10 | 839.57 |

物理池读取后保持低占用，但仍有访问成本。压缩路径的低空闲读数会随私有 RAM 恢复而回升；频繁重新访问时，应把这部分成本纳入选择。不同路径还改变块大小、准入与 IPC，不能把全部耗时差异归为压缩算法成本。
