# 闲置 VM 能省多少内存，恢复要等多久？

## 主要结论 {#conclusions}

**Linux 上，持久保留的重复内容 Job 快照通过压缩同时减少刚捕获后的计费页缓存和保留存储，代价是 suspend 更慢；SDK offload 压缩节省 backing 存储，而不是停驻内存。** 按实际数据支持的存储/缓存收益选择压缩，不把它当作普遍的活跃 VM 内存或容量提升。

既有冻结公开批次；每格 N=30，P50，raw → compressed。两种机制来自独立批次，不构成跨机制比较。

| 使用场景 | 有证据支持的压缩收益 | 代价 / 选型含义 |
|---|---|---|
| 保留重复内容的 Job 执行快照 | 刚捕获后的停驻 cgroup 内存 **308.43 → 33.28 MiB**，主要减少计费页缓存；保留 Job 分配块 **122.76 → 41.04 MiB** | suspend **960.08 → 1082.81 ms**；配对差异 +122.73 ms，95% CI [+111.82, +135.54]。缓存可回收，因此这不是容量结论 |
| 停驻重复内容的 SDK VM | backing 分配块 **181.72 → 15.65 MiB**，但停驻内存 **30.64 → 32.07 MiB** | offload **45.31 → 427.79 ms**；压缩是存储取舍，不是额外的停驻内存回收 |
| 回收运行中 Linux VM 的冷页 | 当前实例内 live 压缩仍属实验性功能 | 尚无已完成的公开多轮批次支持内存或恢复的数值结论；见[机制与证据范围](../../design/memory-optimization/compression-local.md) |

这些历史测量尚未针对新集成的产品重新验证，不衡量版本发布带来的改进，也不证明优于 Docker、Firecracker 或其他运行时。

## Motivation {#motivation}

等待模型响应时，VM 的驻留内存会限制可同时保留的环境数量。你还需要知道省下的内存是否转移到文件缓存或压缩池，以及下一次工具执行要等待多久。只有把停驻占用和完整恢复结果一起测，才能判断是否值得暂停或压缩。

## 实验设计 {#interpretation}

<a id="experiment-design"></a>

B-VM-MEMORY 的既有冻结公开批次使用 Linux x86_64/KVM，分别测 SDK 的 whole-VM offload 和 Job API 的 raw/compressed 执行快照。每个机制有独立批次；各自在同机随机交替重复数据/确定性随机数据与 raw/压缩四种条件，每格 30 个新 VM、3 次预热。两核亲和性和总 CPU 配额、2 GiB cgroup、零 swap、256 MiB guest 保持一致。工具与固件预先准备，缓存为热态，不做全局驱逐。

每个 VM 完整校验 64 MiB 私有数据及恢复后的执行状态；这不是整个 guest 工作集的大小，SDK 的输入构造还会留下额外副本和可变状态。主要内存指标是整个受限 cgroup 的 `memory.current`，包含 VM、采集与恢复进程、backing 和计入该组的页缓存；anon/file/kernel 与 CPU 也保留。SDK 在活跃和 offload 后分别静置两秒再取点；Job 在确认运行/暂停后取点，不能把两种机制的绝对值组成排名。

每个冻结批次为 30 个样本 × 四种条件（120 个有效正式样本），全部通过完整数据校验，没有 OOM、失败或耗时剔除。SDK 的 resume 确认与首次完整扫描分别计时；Job 的 resume-to-completion 包含剩余 guest 等待，首次扫描由 guest 单独计时。CPU 是整个 cgroup 的阶段增量，包含控制与后台工作。单 VM 的回收量不回答内存压力下的停驻容量；macOS 自动冷页池、容器 pause 与 Firecracker/QEMU 的同工作集恢复对照尚未完成复测。

公开证据要求批次完成预定样本数，具有冻结源码/二进制/输入来源、相同资源预算、完整恢复正确性校验，并通过预先声明的干扰门禁。受污染或未完成的批次不具备资格；工程 A/B 与诊断观察不能提供公开数字或补齐缺失条件。执行快照、SDK offload 与运行中自动冷页压缩保持为不同机制。

## 实验数据和分析 {#results}

<a id="experiment-data"></a>

### 停驻物理内存与存储 {#measurements}

每格 N=30，数值为 P50。物理内存单位 MiB，存储为文件 `st_blocks × 512` 之和：SDK 仅计 backing，Job 计整个保留 Job。它不是逻辑 RAM 大小，也不是剔除 reflink 共享后的独占磁盘量。

| 机制 | 数据 | 存储 | 活跃物理内存 MiB | 停驻物理内存 MiB | backing / Job 分配块 MiB |
|---|---|---|---:|---:|---:|
| SDK offload | 重复 | raw | 230.56 | 30.64 | 181.72 |
| SDK offload | 重复 | compressed | 388.96 | 32.07 | 15.65 |
| SDK offload | 随机 | raw | 234.85 | 30.63 | 186.97 |
| SDK offload | 随机 | compressed | 406.45 | 32.19 | 144.33 |
| Job 执行快照 | 重复 | raw | 142.31 | 308.43 | 122.76 |
| Job 执行快照 | 重复 | compressed | 142.40 | 33.28 | 41.04 |
| Job 执行快照 | 随机 | raw | 142.52 | 308.49 | 122.76 |
| Job 执行快照 | 随机 | compressed | 142.36 | 101.98 | 175.01 |

SDK 的 raw 和压缩停驻占用接近；压缩活跃阶段还计入较多文件缓存，不能说压缩让活跃 VM 更省内存。Job raw 停驻时约 297 MiB 来自文件缓存，重复/随机压缩分别约 21/88 MiB。文件缓存可在压力下回收，因此快照刚生成后的差距不能直接乘以环境数量推算容量。随机数据的压缩 Job 分配块反而高于 raw，存储收益取决于数据。

### 暂停、恢复访问与 CPU

每格 N=30，单位 ms。单一分布给 P50；分簇单元格给“簇样本数/30：簇中位数”，两簇不能合并成一个 P50。

| 机制 | 数据 | 存储 | offload / suspend ms | 恢复后首次完整扫描 ms | 活跃→停驻 CPU ms | 停驻→恢复/结束 CPU ms |
|---|---|---|---:|---:|---:|---:|
| SDK offload | 重复 | raw | 45.31 | 108.47 | 34.34 | 155.66 |
| SDK offload | 重复 | compressed | 427.79 | 13/30: 125.09; 17/30: 266.51 | 412.50 | 13/30: 320.26; 17/30: 515.59 |
| SDK offload | 随机 | raw | 56.87 | 123.65 | 43.05 | 163.68 |
| SDK offload | 随机 | compressed | 479.88 | 714.49 | 449.46 | 919.80 |
| Job 执行快照 | 重复 | raw | 960.08 | 151.88 | 827.26 | 392.50 |
| Job 执行快照 | 重复 | compressed | 1082.81 | 152.27 | 780.01 | 425.59 |
| Job 执行快照 | 随机 | raw | 1020.27 | 151.65 | 825.33 | 391.85 |
| Job 执行快照 | 随机 | compressed | 1538.23 | 152.17 | 908.76 | 437.94 |

SDK 重复数据的压缩首次恢复扫描分成 13/30 和 17/30 两簇，分别约 125 和 267 ms；随机数据约 714 ms。SDK raw 的 warm scan 约 25 ms；压缩 warm scan 也分簇（重复数据 25/30 为 25.10 ms、5/30 为 38.53 ms；随机数据 20/30 为 25.03 ms、10/30 为 38.57 ms）。分簇原因未验证，不能仅靠一个中位数给恢复预算。

Job warm scan 约 49 ms，恢复后约 152 ms。其 resume-to-completion 为 8.28–8.35 秒，包含约八秒剩余 guest 等待，不能当作恢复本身需要八秒。完整命令耗时和恢复首次扫描的指标不可互换。

### 与已有方案的证据范围 {#linux-lifecycle}

| 方案 | 可用证据 | 容量选型仍需什么 |
|---|---|---|
| pVisor Linux SDK offload / Job 快照 | 物理内存、存储、阶段 CPU、完整恢复数据；两种机制分开 | 压力下可恢复停驻环境的完整扫描 |
