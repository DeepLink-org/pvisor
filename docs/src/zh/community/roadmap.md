# 路线图

当前重点是单机执行的可靠性、共享资源成本与接口一致性。原生 Job、逐容器 VM 和 daemon SDK 已有独立入口；下面的工作补齐各自合同与验证，不以并发实例数定义监督级别。

| 工作 | 验收标准 |
| --- | --- |
| 本地生命周期与暂存可靠性 | macOS/Linux 的完成、取消、超时、fork 和分批 apply 路径有回归；失败后可检查记录及剩余改动 |
| 边界与证据一致 | 按执行器验证文件和网络控制，Bundle 区分计划、安装回执、未观测与零计数；缺失控制不被标签掩盖 |
| Gateway 捕获可靠性 | 有界队列、提交失败、关闭和恢复有回归；明确入队与持久提交的差别 |
| Replay 兼容性 | 每个适配器固定受支持版本，验证完整工具批次和第一次续跑请求边界；实验报告记录样本及局限 |
| 文档与分发一致 | 入口示例可运行，默认行为只有一处权威定义 |

新增公开功能前，应具备实现入口、验证场景、限制说明和发布记录。改变数据契约、执行边界或公开命令时，先明确兼容策略和验收方式。

## 安装与集成 {#installation-and-integration}

计划中：先让用户完成安装、首次执行和暂存审查，再扩展分发渠道与语言 SDK。
[分发提案](releasing.md#distribution-plan)定义各渠道的定位和共享产物方向；
当前可用命令以[安装指南](../start/installation.md)为准。

下一步是独立二进制归档、版本化安装器和 Homebrew 入口，并完善安装诊断、升级、
回退与卸载。CLI 的 JSON 输出、事件、错误与兼容策略先收敛，TypeScript／Python
SDK 再由实际平台集成需求驱动。npm 分发与 SDK 独立评估，不作为 CLI 发布前置条件。

Linux host 的选择性出口目前仍使用协作式代理，不能因 `--safe` 标签宣称不可绕过。
拟补齐受控代理出口与宿主网络隔离的组合，并验证清除代理变量、直接 socket 和
辅助进程访问等路径。现有强制出口选项及各平台差异见
[网络边界](../guides/policies/network.md#网络边界)。

## 惰性镜像的小文件供给优化 {#lazy-image-small-files}

已实现：V2 将全部元数据放入压缩目录 radix 索引，小文件按目录打包，数据 frame 独立解压；服务器、文件系统、S3 和 Docker 本地池统一使用这套格式。V1 存储已退役，需要从 OCI 重新发布；细节与限制见 [Lazy Image V2](../design/lazy-image-v2.md)，本地合成负载结果见[工程 A/B](../lab-notes/image-format-performance-analysis.md)。

下一步验收：

- 在真实 Python import、Node.js 依赖加载和编译／测试中测量首次有效工具调用、完整任务耗时、P95/P99、S3 请求数、下载字节与解压放大。
- 分开覆盖冷元数据、冷内容、暖缓存与多任务并发，计入首次发布成本；当前本地存储微基准不能代替这些结论。
- 在现有有界缓存与 miss 合并之上评估相邻请求合并及预取，避免无用读取；验证 mmap、copy-up、导出及远端故障。
- 改善发布器 O(N) 元数据规划与单索引 64 MiB 上限；设计 pack 引用保留和安全 GC，不按年龄删除共享内容。

## 单机 daemon {#daemon}

[Daemon](../guides/daemon/index.md) 已提供镜像准备、默认原生 guest 引擎，以及 OpenSandbox 1.1.0/E2B Python SDK 2.59.0 核心流程的真实 VM 验证。后续重点是扩大协议回归、生命周期故障恢复和固定预算测量。Stage/apply、checkpoint/fork API 和自动 node 资源获取仍未接入；完整 SDK 一致性、生产密度与敌对多租户保证仍需独立验收。

## L2 与 L3 里程碑

!!! note "建设中"
    L2/L3 的进入条件与缺口清单尚未定稿，排期未确定。以下列出当前要求与验收标准。级别定义见[监督等级与执行规模](#trust-ladder)，容量依据见[并发密度](../benchmarks/density.md)。

### L2：策略与证据门禁

进入条件（待定稿）：在已有本机并行流程上明确免审规则、证据要求与失败回退；并发上限与资源模型作为容量规划依据，见[并发密度](../benchmarks/density.md)。

验收标准：

- 批量审查流程可复现：按 workspace 聚合、批量 apply，见[单机多 Agent 并行与批量审查](../guides/parallel-agents.md)。
- CI 接入给出可复制的 workflow 示例，明确 `apply` 的语义（谁审、何时合），失败与超时路径有回归，见[在 CI 中运行 Agent](../guides/ci.md)。

### L3：集群化执行、集中证据

进入条件（待定稿）：明确与调度器的边界——pVisor 提供执行语义与证据，跨节点编排交给 Kubernetes、Ray，见[集群化执行](../design/research/index.md)。

验收标准：

- 给出外部跨节点调度器集成及证据集中后审计的缺口清单和阶段划分。pVisor 不提供集群总控；单机 daemon 没有全局 DAG 或分布式 lease。
- 容量依据与 L2 共用[并发密度](../benchmarks/density.md)。

## 监督等级与执行规模 {#trust-ladder}

L0–L3 保留为监督方式的参照：L0 逐条批准，L1 逐项审查，L2 按策略与证据抽查，L3 以审计和例外处理为主。执行规模可以是单个任务、本机并发，或由外部系统调度多台机器；它与人工介入方式是两条独立的轴。增加并发不会自动建立 L2/L3 的接受规则，上述里程碑仍需满足各自的进入条件与验收标准。
