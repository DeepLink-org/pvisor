# 四实例直接转发优化：延迟和 CPU 有收益，吞吐提升尚未确认

## Motivation

批量收发、减少中间复制和按需服务 smoltcp，降低了四个真实 pVisor VM 的通信延迟和 CPU 消耗。短批传输的吞吐仍有较大波动，未检出稳定提升；这些改动也没有消除 VM 启动阶段已有的偶发退出问题，不能据此宣称整体运行已无故障。

30 对有效正式样本中，全互连 RPC RTT P50 中位数从 **359.00 µs 降至 344.92 µs**，四跳 RPC 从 **940.24 µs 降至 922.46 µs**。48 MiB 聚合批传输的四实例累计 CPU 从 **0.9028 秒降至 0.8457 秒**；吞吐的配对差 95% 区间跨零。每实例宿主内存硬上限均为 **512 MiB**，该完整批次没有校验失败、OOM 或样本剔除。

## 实验设计

测量逐字节校验通过的应用吞吐、RPC 往返时间和实例 cgroup 累计 CPU，作为四实例通信成本。它们反映固定资源预算下应用完成通信的速度及消耗。延迟和 CPU 越低、有效吞吐越高，同样预算可完成的通信越多。

工程对照登记为 [B-FOUR-PEER-ENG](../README.md#b-four-peer-eng)。基线为 `314693c8` 的 GNU release 构建，候选从该提交的独立源码副本构建，只改变 OverlayNet peer 收发、帧解析及 VMM virtio-net 私有实现和对应测试，共六个运行时源码/测试文件。没有把工作区同时进行的文件系统、镜像缓存或 CLI 改动带入候选。两个制品使用相同静态 musl worker、镜像、冻结固件和编译参数；固件为本地 `libkrunfw.so.5.6.2`，guest Linux `6.12.109`。

候选的具体行为为：

- peer 接收一次最多排空 32 个已就绪 datagram，向 guest 一次最多 gather write 32 帧；不等待凑批，不拼接复制 payload，保留短写游标和背压。
- guest→peer 转发直接借用帧解析缓冲区，去掉中间 `Vec`；只有进入 smoltcp 的帧才分配其拥有的副本。
- peer-only 事件不触发无用的 smoltcp 全套轮询，也不延后已设定的协议栈 deadline；公平选择事件，避免持续 peer 流量饿死 DNS、普通出口或关闭处理。
- VMM 用有界读前缓冲区解析 Unix stream，合并多个完整帧的 `recv`；半个长度头、半帧及 EOF 不再进入阻塞 `MSG_WAITALL` 循环。非法长度在复制前拒绝。
- RX 遵循已协商的 EVENT_IDX，按需通知 guest；只在延迟帧等待新 buffer 时请求 guest kick，并重查可用队列以关闭补充 buffer 的竞态。补交延迟帧也会执行完成通知。

保持 MTU 1500、1514 字节 peer 帧上限、代际 fencing、来源验证、原有丢弃规则和无公共转发进程的设计。没有启用 GSO：现有 peer 协议不能直接接受大帧，需另做能力协商、checksum/segmentation 和正确性验证。

宿主为 AMD Ryzen 7 9700X、Linux `7.2.11-200.fc44.x86_64`，Rust `1.98.1`。每条件启动四个新 KVM VM：各 384 MiB guest RAM，整个实例 scope 限制 512 MiB、swap 0、1 CPU quota，逐线程验证 affinity 为 CPU 4–7；控制器在 CPU 8–9。两臂顺序运行，预声明 3 对预热、30 对 seeded 随机正式样本。全互连 RPC 为 12 方向各 500 次 256 字节 echo；批传输为每方向 4 MiB、合计 48 MiB；四跳环形 RPC 为四节点各 200 次 256 字节请求。准备和启动不计入网络时钟；CPU 是四个实例操作窗口的合计，含 guest 内核、VMM、应用校验及输出。

所有有效慢样本保留，错误使整批失败，不拼接批次。入场和每 0.5 秒检查可见的同用户外部构建、测试及 KVM 进程；发现干扰即判整批无效，不终止外部任务。不可读进程仍是覆盖缺口。正式样本没有注入 profile。统计为每轮指标的中位数及 5,000 次配对 bootstrap 95% 区间；延迟先取轮内 RTT P50/P95，再取 30 轮中位数，P95 仅参考，不报 P99。逐轮分布已检查，短批传输波动宽，未见清晰分离的双峰。

本对照测量整个改动组合，不能分别归因各项收益；也没有重测 Docker，不能拿旧 Docker 批次计算优化百分比。长时间满载、UDP 极限 offered load、跨宿主和生产密度不在有效正式结论内。

## 实验数据和分析

**有效正式批次：N=30 对，差值为候选减基线。**

| 指标 | 基线中位数 | 候选中位数 | 配对差中位数 [95% CI] |
|---|---:|---:|---:|
| 全互连 RPC RTT P50，µs | 359.00 | 344.92 | −15.16 [−17.19, −13.19] |
| 全互连 RPC RTT P95，µs，参考 | 597.66 | 571.04 | −30.92 [−37.47, −23.98] |
| 四跳 RPC RTT P50，µs | 940.24 | 922.46 | −18.62 [−21.98, −13.49] |
| 四跳 RPC RTT P95，µs，参考 | 1,152.89 | 1,132.98 | −22.96 [−29.07, −10.75] |
| 批传输有效吞吐，Gbit/s | 1.274 | 1.416 | +0.131 [−0.004, +0.260]，未检出差异 |
| 全互连 RPC：累计 CPU 秒 | 0.7383 | 0.7067 | −0.0296 [−0.0399, −0.0254] |
| 批传输：累计 CPU 秒 | 0.9028 | 0.8457 | −0.0651 [−0.0821, −0.0513] |
| 四跳 RPC：累计 CPU 秒 | 0.6452 | 0.6334 | −0.0105 [−0.0141, −0.0084] |

延迟和 CPU 下降的区间均未跨零，收益明确但幅度有限。吞吐不能仅按中位数变化宣称提升：基线范围为 0.960–1.603 Gbit/s，候选为 0.799–1.772 Gbit/s，候选也有更慢样本。它尚不能替代此前 Docker bridge 对照中观察到的性能差距。

**资源和完整性复核，包括预热共读取 792 个客户端原始输出：**

| 检查 | 基线 | 候选 |
|---|---:|---:|
| 正式样本最高单实例 `memory.peak`，MiB | 46.42 | 46.72 |
| 每实例 `memory.max`，MiB | 512 | 512 |
| OOM / OOM kill / memory max 事件 | 0 / 0 / 0 | 0 / 0 / 0 |
| 30 轮全互连 RPC 校验次数 | 180,000 | 180,000 |
| 30 轮四跳 RPC 校验次数 | 24,000 | 24,000 |
| 30 轮批传输校验数据，GiB | 1.40625 | 1.40625 |
| 完整正式批次失败 / 剔除 | 0 / 0 | 0 / 0 |

内存数字是 cgroup 归属记账，负载没有触碰全部 guest RAM，不能解释为满载 VM 只需约 47 MiB。RPC / bulk / ring 的 CPU quota throttling 事件分别为基线 16 / 13 / 0、候选 14 / 13 / 0，未排除受限样本。146 次正式干扰检查均没有命中可见外部工作。

独立故障预检的两臂均通过 12 方向 DNS、暂停一条接收流读取 1 秒时其他流继续通信、停止节点后剩余三个节点通信，以及节点重启后的全互连恢复。测试覆盖也通过：OverlayNet **89/89**；隔离候选 VMM（启用 net）**590/590，8 项既有跳过**。新增用例验证短写、逐字节碎片、截断 EOF、超长帧、队列耗尽后补交通知，以及持续恶意 peer 包下 DNS 和关闭的推进。定向 clippy 和 warnings-denied rustdoc 通过，CLI/gateway release 构建通过。Linux 是实际运行平台，未验证 macOS。

**独立系统调用诊断，不作为性能样本：**同样的故障预检中，VMM 网络线程的 `recv` 累计检查点从约 170,550 次降至 51,966 次，后端 `writev` 从约 71,407 次降至 28,964 次。它们支持“减少每帧 socket 调用”的方向，但计数器按线程每 1,024 次写检查点，退出未刷新的尾部是下界；含控制/恢复流量，也不能用 syscall 墙钟时间当 CPU profile 或精确 IRQ 降幅。

**失败批次和未解决的启动风险：**

- 另一个初始对照在第 2 个含预热轮次遇到候选启动退出 125，未产生 guest 输出；整批无效。同期观察到其他构建/KVM 工作，但没有证据证明它导致退出。
- 独立 384 MiB 持续批传输补测，在第 25 个含预热配对轮次遇到候选节点启动退出 125；整批停止，不发布已完成部分的吞吐均值、重传率或显著性，也没有重试补选。该批干扰检查没有命中外部工作。
- 启用 VMM 日志的独立重复启动诊断，在第 47 个四节点组中也复现了**未优化基线**退出 125，日志为 `VM shutdown without workload status: vcpu_exit=None`。这证明基线同样存在启动风险，但尚未确定根因，也未定量排除候选改变发生率的可能。启动诊断不混入网络计时。

已进入通信的上述样本未见内容校验失败；启动失败仍使对应整个实验无效。完整正式批次的零失败只适用于该批覆盖场景，不能扩大为长期稳定性承诺。额外启动错误应作为独立的 VM bootstrap 问题继续定位。

工作区全量 VMM 测试另有并行文件系统改动的 ownership 用例失败；该用例不在冻结基线及候选内，没有通过修改该用例或混入文件系统修复来获得网络测试通过。
