# 四个 pVisor 在 512 MiB 上限下的通信测试与 Docker 对照

## Motivation

四个真实 pVisor VM 在本次全互连、多跳、慢接收端和节点停启测试中均能正确通信，内存硬限制也已生效。性能明显落后于 Docker 自定义 bridge：当前实现能够完成这些负载，但尚不能视为 Docker bridge 的性能替代。

30 对正式样本中，pVisor 的全互连 TCP 聚合有效吞吐中位数为 **1.366 Gbit/s**，Docker 为 **10.139 Gbit/s**；256 字节 RPC 往返中位数分别为 **361.1 µs** 和 **11.37 µs**。四跳 RPC 分别为 **943.9 µs** 和 **19.68 µs**。所有样本均完成数据校验，无 OOM、无失败、无样本剔除。

本报告使用真实 KVM guest。此前约 5.35 Gbit/s 的结果是 backend 线程之间的 Ethernet 帧微基准，未经过真实 guest 内核和 virtio，不能用于替代这里的应用层数据。

## 实验设计

测量校验通过的应用数据吞吐、RPC 往返延迟，以及实例 cgroup 的 CPU 和内存，作为四实例通信成本。它们反映受限实例同时进行网络通信时的完成速度和资源消耗。吞吐越高、延迟和资源消耗越低，同样的资源预算能完成的通信越多。

| 条件 | pVisor | Docker |
|---|---|---|
| 实例数 | 4 个原生 KVM VM | 4 个 rootful 容器 |
| 每实例硬内存上限 | 整个 owner/VMM/网络后端/run 前端 scope：512 MiB | 容器 cgroup：512 MiB |
| guest 内存 | 配置 384 MiB；guest 实测可见约 391 MiB | 共享宿主内核，以 cgroup 限制内存 |
| swap | 0 | 0 |
| 每实例 CPU | 1 vCPU，整个 scope 同时限制为 1 CPU quota | 1 CPU quota |
| CPU 范围 | 实际线程 affinity 为逻辑 CPU 4–7 | cpuset 为逻辑 CPU 4–7 |
| 网络 | 新增的直接 Unix datagram peer 网络 | 独立 Docker 用户 bridge |
| 地址与 MTU | `10.231.70.11`–`.14`，MTU 1500 | 相同 |
| 用户程序 | 同一份静态 musl 二进制；镜像内文件独立核对 SHA-256 一致 | 相同 |

宿主为 AMD Ryzen 7 9700X、Linux `7.2.11-200.fc44.x86_64`；Docker Engine 为 `29.8.2`。pVisor 使用源码的 GNU `release` 构建，运行时代码基于 `3b1c5744`，搭配冻结的本地 `libkrunfw.so.5.6.2`，guest 为 Linux `6.12.109`。本次没有重新构建当前 `fw/` 目录。具体制品身份见[收据](.data/four-20261024/artifact-receipt.json)和[镜像内 worker 校验](.data/four-20261024/worker-identity.json)。

用户的 systemd 子树没有委派 cpuset controller，因此 pVisor 通过 `taskset` 约束线程，并逐线程检查实际 affinity；CPU quota 和内存限制直接检查内核 cgroup 文件。控制器与采样器位于 CPU 8–9。Docker 的 dockerd、containerd、shim、控制客户端，以及共享宿主内核的部分工作不在容器预算内；报告另外保留 dockerd/containerd 的 CPU/RSS 观察值，不把它们视为零成本。这不是两个完整系统在相同整机 cgroup 内的纯转发机制对照。

三个正式负载按固定顺序执行，全部使用 TCP，连接在 GO 屏障前建立：

| 负载 | 拓扑和数据量 | 计量方式 |
|---|---|---|
| 全互连 RPC | 每节点同时连接其他 3 节点，共 12 条有向链路；每链路 500 次 256 字节 echo，共 6,000 次 | 每次请求的往返时间；发送内容与回复逐字节比较 |
| 全互连批传输 | 12 条有向链路同时各发送 4 MiB，共 48 MiB；每块 64 KiB | 接收端逐字节验证并回复累计校验值；总有效字节除以最慢客户端耗时 |
| 四跳环形 RPC | 每节点发起 200 次 256 字节请求，经相邻节点依次绕四节点一圈，响应原路返回，共 800 次 | 计一次原始应用 payload，不把每跳重复转发的字节累加为吞吐 |

每个条件创建四个新实例，执行后销毁，两个运行时不同时运行。3 对预热后，按固定随机种子交替运行 30 对正式样本。镜像准备、实例启动、客户端启动和屏障等待均不计网络时钟；正式执行顺序为 RPC → 批传输 → 环形 RPC，因此不称冷邻居缓存测试。宿主页缓存保留。全部有效慢样本保留；任何数据、资源或清理检查失败都会停止批次。

延迟表取每轮请求 RTT 的 P50/P95，再对 30 轮取中位数；P95 是参考值，未报告 P99。配对差为每轮 pVisor 减 Docker，使用 5,000 次配对 bootstrap 给出 95% 区间。没有合并不同批次。完整分布和四分位数已检查，批传输存在较宽波动，未见清晰分离的双峰。

CPU 是网络操作窗口内四个实例 cgroup 的累计 CPU 秒，包含 guest/VMM、校验程序及结果输出等工作，不能解释为转发函数独占成本。每 50 ms 采样 cgroup；短暂内存峰值另外由内核 `memory.peak` 保留。内存是 cgroup 归属记账，共享文件页、既有缓存和宿主内核并不全部归入每个实例。负载没有触碰全部 guest RAM，因此内存读数不能外推为满载 VM 的大小或生产密度。

## 实验数据和分析

**吞吐和延迟，N=30 对正式样本：**

| 指标 | pVisor 中位数 | Docker 中位数 | 配对差中位数 [95% CI] |
|---|---:|---:|---:|
| 全互连批传输有效吞吐，Gbit/s | 1.366 | 10.139 | −8.798 [−8.988, −8.596] |
| 全互连 RPC RTT P50，µs | 361.06 | 11.37 | +350.24 [+347.09, +352.47] |
| 全互连 RPC RTT P95，µs，参考 | 601.35 | 28.20 | +574.41 [+564.38, +580.21] |
| 四跳 RPC RTT P50，µs | 943.87 | 19.68 | +924.18 [+921.42, +928.35] |
| 四跳 RPC RTT P95，µs，参考 | 1,159.51 | 27.82 | +1,132.55 [+1,119.14, +1,144.68] |

同批中位数水平下，Docker 批传输吞吐约为 pVisor 的 7.4 倍；pVisor 全互连 RPC 延迟约为 Docker 的 31.8 倍，四跳约为 48.0 倍。配对差区间均未跨零，差距不能解释成一次运行的偶然波动。批传输的逐轮范围为 pVisor **0.962–1.631 Gbit/s**、Docker **9.334–10.769 Gbit/s**，没有删除较慢结果。

**实例 cgroup 资源：**

| 指标 | pVisor | Docker |
|---|---:|---:|
| 每实例 `memory.max` | 512 MiB | 512 MiB |
| 正式样本中最高单实例 `memory.peak` | 43.91 MiB | 11.22 MiB |
| OOM / OOM kill / 内存 max 事件 | 0 / 0 / 0 | 0 / 0 / 0 |
| 全互连 RPC：四实例累计 CPU 秒，中位数 | 0.741 | 0.024 |
| 批传输：四实例累计 CPU 秒，中位数 | 0.917 | 0.149 |
| 四跳 RPC：四实例累计 CPU 秒，中位数 | 0.651 | 0.012 |

pVisor 在三个场景分别观察到合计 14、10、1 次 CPU quota throttling 事件；Docker 均为 0。配额影响已经包含在结果里，没有筛掉受限样本。dockerd/containerd 的窗口累计 CPU 增量中位数约为 Docker RPC 0.01 秒、批传输 0.01 秒、环形 RPC 0 秒；该读取以宿主调度 tick 为粒度，不等于服务真实零开销，也未覆盖全部 shim/宿主网络工作。

Docker 批传输窗口结束时，dockerd、containerd 的 RSS 快照中位数分别约为 123.6 MiB 和 58.1 MiB，见[服务内存观察](.data/four-20261024/daemon-memory.json)。它们是既有共享服务的进程 RSS，不能直接与容器 cgroup 内存相加作为本实验的新增物理占用；上表也不代表 Docker 完整部署只有每实例 11.22 MiB 的成本。

**正确性与故障恢复：**

- 每个运行时的 30 个正式样本累计完成 **180,000 次全互连 RPC、24,000 次四跳 RPC，以及 1.406 GiB 批传输**，全部完成应用内容校验。另有 3 对预热，不混入上述统计。独立复核共读取了包括预热在内的 792 个客户端原始输出。
- 真实四节点预检中，两个运行时的 **12 个方向名称解析全部正确**。
- 将一条 TCP 流的应用接收端暂停读取 1 秒，同时进行其他 RPC：pVisor 的四条健康 RPC 流最晚约 **125.5 ms** 完成，慢流约 **1.063 s** 完成；Docker 分别约 **2.76 ms** 和 **1.017 s**。这是单次故障预检，说明健康流可以继续推进，不作为正式性能分布。
- 停止节点 1 后，其余三个节点完成通信；重新启动节点 1，在额外等待 400 ms 后，全互连 RPC 校验通过。这里验证的是正常停启恢复，没有测量精确恢复下界，也没有把它描述为故障期间可靠送达。
- 正式批次 **0 失败、0 剔除**。[准备诊断](.data/four-20261024/preparation-diagnostics.json)记录了缺失固件、未委派 cpuset 的准备问题，另保留修正后的完整预检；这些诊断没有混入正式数字。

这些结果支持“覆盖场景内通信正确且能恢复”，不能证明无限时长或任意规模下无故障。应用使用 TCP；没有采集链路级丢包与 TCP 重传计数，应用最终校验通过不代表网络没有丢过包。

现有 pVisor 路径包含 guest 内核、virtio-net、VMM、Unix datagram 转发及多次调度；Docker bridge 走共享宿主内核。本实验没有逐段 profile，不能把全部差距归因于某一个环节。下一步应先测量 virtio 唤醒、每帧系统调用和调度成本，再评估批量收发；本报告不宣称这些成本已经解决。
