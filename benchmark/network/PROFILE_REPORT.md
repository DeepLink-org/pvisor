# 网络栈按速度编译能改善哪些场景？

## Motivation

仅将 `pvisor-overlaynet` 和 `smoltcp` 从 release 的体积优化改为速度优化，
在本地真实 KVM 的六个 bulk 场景均有显著收益：配对吞吐提高 43.6%–136.5%。
建连和 RPC 延迟下降 7.1%–11.4%；合成 DNS、定时小块流的完整耗时、首字节和
事件间隔未检出差异。建议优先采用这两个 crate 的局部速度优化，而非先替换协议栈。

这是工程 A/B，不是公网速度或用户下载时间的承诺。产品默认 release 采用了这两个
crate 的局部速度优化，没有将全程序切换为 `performance`。候选可执行文件只增加
68,288 B（66.69 KiB，0.312%），没有增加 flow/队列预算、调整 TCP 参数或改变网络策略。

## 实验设计

测量 worker 内的单调网络耗时与经完整校验的 wall goodput，作为各场景延迟和有效吞吐。
它们描述该负载在给定 guest/宿主资源下完成网络通信的能力。延迟越低或吞吐越高，
相同通信任务的等待越少。

- **平台：** Linux x86_64/KVM，AMD Ryzen 7 9700X（8 核/16 线程），Fedora
  内核 `7.3.3-300.fc45.x86_64`；Rust 1.98.0。宿主 CLI target 为
  `x86_64-unknown-linux-gnu`，无 Gateway feature；guest/服务端/原生客户端复用
  同一份 `x86_64-unknown-linux-musl` 静态 worker。未测发行包的完整 musl CLI。
- **制品：** 同一源码、Cargo.lock、features、固件和 worker。基线为原始 release；
  候选仅通过 `profile.release.package.pvisor-overlaynet.opt-level=3` 和
  `profile.release.package.smoltcp.opt-level=3` 构建。其他运行时 crate 的优化级别
  与 features 未变；Cargo 同时把 smoltcp build script 的编译级别从 `0` 改为 `3`。
- **资源与出口：** 每个样本新建 2 vCPU/256 MiB guest，CLI/VMM/网络线程固定 CPU
  0–3，原生客户端也固定 CPU 0–3；服务端 CPU 4–5，只监听 loopback。
  guest 经合成 DNS、域名/端口 allowlist 和正常 host TCP connector 访问服务。
  原生客户端与 guest 可用应用 CPU 数不同；原生仅作绝对参考，不作等预算排名。
  没有宿主 CPU quota 或整机内存硬限制，guest RAM 不是宿主 RSS 上限。
- **采样：** 3 轮预热、30 轮正式运行；每轮三个条件和场景次序 seeded 随机交替，
  同轮各条件的场景次序相同。一个新 VM 是一个独立样本；同 VM 的 128/256 次请求
  不冒充独立样本。共 90 个正式执行（其中 60 个真实 VM），另有 9 个预热执行。
- **时钟：** 建连取 128 次 connect/configure 的批次中位数；新连接 RPC 为
  128 次 1 KiB 请求/回显，长连接 RPC 为 256 次；DNS 为 128 次合成查询。
  bulk 各场景总量 64 MiB，线程启动与建连在时钟外，数据生成、传输、逐字节校验
  及上传服务端回执在时钟内。流为 32 个 64 B 事件，服务端间隔 2 ms；
  首字节包含建连和协议头，完整时钟包含服务端的预定等待。VM 启停不计网络指标。
- **正确性与干扰：** 全部命令零退出，payload 逐字节校验，每个 VM 的 Bundle
  确认真实 VM 与不可绕过的 smoltcp；另外核对精确流数、DNS 数、双向字节计数和
  零失败/拒绝。正式样本均无 cargo/rustc 构建干扰，没有删除或补选慢样本。
  宿主仍有其他负载，观察到的 1 分钟 loadavg 为 7.78–10.85，未推断分簇原因。

下表括号为簇内样本数，每条件总 N=30；分簇门槛为相邻有序值间隔大于
`max(0.005, 0.1 × 该条件中位数)`，每簇至少三个值，0.005 使用该行展示单位。
这是预先实现的描述规则，不是剔除或归因。CI 为 5,000 次配对 bootstrap；
差异是逐对差值的中位数，百分比是逐对相对变化的中位数，并非两个簇的比值。
不报告 P99，P95 仅在原始 summary 中作为参考。

## 实验数据和分析

### 大流量：提高 43.6%–136.5%

吞吐单位 MiB/s，越高越好；差异 CI 的单位也是 MiB/s。

| 场景 | release：簇中位数（N） | 网络 O3：簇中位数（N） | 配对增加 [95% CI] | 配对变化 |
|---|---|---|---|---:|
| 单连接下载 | 138.08（18）；288.75（12） | 179.50（18）；430.59（5）；528.82（7） | +65.12 [45.49, 147.55] | +43.6% |
| 单连接上传 | 157.40（12）；202.50（4）；257.04（14） | 380.82（30） | +154.02 [140.15, 184.71] | +92.2% |
| 8 连接下载 | 181.76（15）；372.38（15） | 286.22（16）；497.97（3）；595.81（3）；671.50（8） | +134.91 [103.28, 237.48] | +59.7% |
| 8 连接上传 | 147.88（15）；268.67（15） | 274.24（14）；671.36（10）；840.76（6） | +281.90 [141.51, 447.50] | +136.5% |
| 32 连接下载 | 154.60（16）；276.65（8）；320.27（6） | 218.93（16）；529.50（14） | +91.53 [65.44, 204.44] | +60.6% |
| 32 连接上传 | 126.27（16）；184.19（14） | 212.40（16）；352.01（14） | +108.83 [90.06, 155.38] | +78.9% |

六项 CI 均不跨零。大量时间确实受当前网络代码的编译优化影响，但同时改变两个
crate，不能把收益进一步拆成 smoltcp 与桥接代码各自的贡献，也没有证明某个具体
checksum、拷贝或扫描函数占了多少时间。多簇仍存在，不能宣称已经解决网络波动。

原生参考分别为单下载 1585.50、单上传 1569.18、8 下载 3381.58、32 下载
3454.86、32 上传 2341.28 MiB/s（均 30 个样本、未分簇）；8 上传为
1913.65（4）和 2679.31（26）MiB/s。候选仍明显低于这份原生参考；
CPU 分配和网络边界不同，不把两者差距全部归因于用户态 TCP 实现。

### 小请求：收益存在，但绝对值较小

单位 ms，越低越好；负差异表示候选更快。

| 场景 | release：簇中位数（N） | 网络 O3：簇中位数（N） | 配对差异 [95% CI] | 配对变化 |
|---|---|---|---|---:|
| TCP 建连 | 0.203（17）；0.262（13） | 0.201（30） | −0.023 [−0.034, −0.011] | −10.7% |
| 新连接 1 KiB RPC | 0.380（30） | 0.349（30） | −0.028 [−0.052, −0.005] | −7.1% |
| 长连接 1 KiB RPC | 0.070（16）；0.121（10）；0.148（4） | 0.062（13）；0.093（11）；0.114（3）；0.135（3） | −0.010 [−0.016, −0.005] | −11.4% |
| 合成 DNS | 0.051（25）；0.095（5） | 0.052（23）；0.074（3）；0.098（4） | −0.002 [−0.009, +0.004] | 未检出差异 |

建连/RPC 的节约量是约 10–28 µs，不可换算成公网模型调用速度提升 7%–11%。
原生建连、新连接 RPC、长连接 RPC 为 0.011、0.032、0.008 ms，均为 N=30 未分簇。
合成 DNS 不包含宿主真实域名解析、递归 DNS 或公网 resolver 延迟。

### 定时小块流：没有检出改善

| 指标 | release：簇中位数（N），ms | 网络 O3：簇中位数（N），ms | 配对差异 95% CI，ms |
|---|---|---|---|
| 32 事件完整读取 | 64.846（30） | 64.759（30） | [−0.328, +0.324] |
| 首事件 | 0.341（5）；0.563（15）；0.855（4）；1.406（6） | 0.302（6）；0.608（20）；1.268（4） | [−0.081, +0.061] |
| 事件间隔的批次中位数 | 2.064（30） | 2.064（30） | [−0.003, +0.003] |

三个区间均包含零。此负载主要含服务端预定的等待，不能据此证明所有 SSE 都不受
协议栈影响；它不覆盖公网/TLS、模型 token 生成、不同 write 时序或丢包。

### 决策与证据

两个网络 crate 的默认 release `opt-level` 局部设为 `3`，保留其他 crate 的
体积策略。原始 A/B 使用默认值改变前冻结的制品与构建记录。没有证据要求先换栈，也没有
测量全程序 `performance` profile、macOS/Windows、peer、WAN、QUIC 或故障恢复。

使用新的默认参数重新构建 GNU CLI，产物与该批次候选逐字节一致，
SHA-256 同为下列候选摘要；CLI 的全局 `z` 和 VM crate 的既有 `3` 保持不变。

- 注册：`B-NETWORK-PROFILE-ENG`；复现与离线审核见 [README.md](README.md)。
- 本地原始证据：`benchmark/network/.data/profile-ab-20261115-a/`；构建证据：
  `benchmark/network/.data/build-20261115T024025Z/`，不随 checkout 分发。
- 测量源码：`54d66cf4485e144e3e939d2adfef79d20eda86e0`，A/B 期间产品源码摘要核对无变化。
- 基线 CLI SHA-256：`f209867d68edd7d950c9d04d69a21286b65ba7e499687b2b0a5467d978f78bac`。
- 候选 CLI SHA-256：`c48f0b2c4c7a43b3b44ac8c76d96aae72265331039af06987a981dfe6b6bd39e`。
- 固件 SHA-256：`6b8bf8378520b50ec2ce8ccc99c1a1b3722cb045bf585d7ac22881e3c9cc4bda`。
- `summary.json` SHA-256：`3816402d1b9be3eadabb0f400014d099a84585b693f0a8992b59a1a82052ced9`。

每个 VM 独立记录 340 条 TCP flow、129 次 DNS 问答，guest→host 201,723,200 B、
host→guest 201,722,184 B；全部通过精确计数和逐字节校验。失败预检单独保留，
没有进入正式批次，也没有覆盖或拼接历史用户网络页。
