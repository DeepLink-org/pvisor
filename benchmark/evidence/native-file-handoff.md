# Rust native：哪些共享文件操作可以少一次往返？

[B-VM-GUEST-ENG](../REGISTRY.md#b-vm-guest-eng) 工程记录。问题是：**在保留可变共享文件的可见性、短写和同步错误时，哪些往返可以省；显式改变发布边界又能省多少？**

## 基线与归因

以已合入 #212 的 `4ee9e3d2` 为基线，不沿用 #209 的数字。[#212 最终 CI](https://github.com/DeepLink-org/pvisor/pull/212#issuecomment-7196945266) 的 Rust 顺序/乱序热读为 19.32/19.51 ms，顺序写/乱序覆写加 `fsync` 为 61.24/56.71 ms。那次 CI 为 PASS；PR 描述里的 25/30 是另一台机器上的另一批测量。Firecracker 使用私有 ext4/virtio-blk，没有监视一个宿主可写目录的义务，不能把两列直接当作传输层 A/B。

在本机 Linux x86_64/KVM、Ryzen 7 9700X、btrfs 上，用新 VM 和保留数据校验的 [原探针](../vm/probe.c) 重测，每次访问 1,024 个 4 KiB 块。两次暂停/`fstat` 间的同一协议实例计数用于 FUSE 归因（减去标记的一个 `GETATTR`）；另在 guest 握手边界读取该 vCPU 的 `KVM_GET_STATS_FD`。包含握手产生的少量退出。计数实验不作为时延样本。

| #212 基线，单次诊断 | 工作负载 FUSE 请求 | userspace MMIO exits | halt exits |
|---|---|---:|---:|
| 顺序热读 | 1,024 `GETATTR`，0 `READ` | 1,036 | 3 |
| 乱序热读 | 1,024 `GETATTR`，0 `READ` | 1,036 | 2 |
| 顺序写 + sync | 1,024 `WRITE` + 1 `FSYNC` | 1,035 | 1,022 |
| 乱序覆写 + sync | 1,024 `WRITE` + 1 `FSYNC` | 1,035 | 1,020 |

两种读慢在每次读取都要确认 size/mtime，不在从盘取 4 MiB 数据。两种写都要知道 host 实际接受了多少字节；一次末尾 `FSYNC` 并不是 1,024 个小写的唯一瓶颈。`ioeventfd` kick、MMIO exit、IRQ 和 FUSE 调用不是同一指标。tmpfs 是 guest 内的匿名页，不能用 FUSE 次数解释它的读写；本次不改 Linux tmpfs 或以它替换共享根目录。

## 默认路径改变了什么

- 单次 `preadv` 的多个目的缓冲区对应**连续文件偏移**。用同一份新鲜属性和同一把 inode 读锁完成散读，不把这份校验借给下一次系统调用。128 次调用、每次 8 个非空目标，预热后计数从 1,024 个 `GETATTR` 降到 128，两个版本都是零 `READ`。
- `SEEK_SET` / `SEEK_CUR` 无需文件长度；去掉查询，不去掉 seekability、偏移和访问检查。128 对 `lseek(SEEK_SET)` + `read` 从 256 次校验降到 128 次。`SEEK_END` 和独立标量 `pread` 仍会观察宿主改变。
- 读过文件不等于映射过文件。只被普通读者使用的干净缓存，在写时丢弃相交页，按调用方的句柄和字节范围发送 `WRITE`。短写只报告已接受部分，失败不把未写数据留在缓存中。VMO 一旦交给外部用户，之后一直保留原映射写回路径。独立的写确认、后端 `FSYNC`、关闭和最终同步均未移到计时外。
- 宿主设备访问在取得 RAM lease 时一次取得 prepare callback；该 callback 只能在设备已经排空时替换。最后一个 lease 只需唤醒正在等待排空的线程，不需每次都广播。保留每次访问前的准备、每个映射的生命周期和 idle 通知。这减少的是宿主工作，而不是 VM exit。

单独替换宿主 RAM 屏障、保持 kernel 不变：15 组随机配对，顺序/乱序标量热读的配对耗时变化为 −4.12% [−4.55%, −3.01%] / −4.87% [−7.69%, −4.31%]。顺序写和乱序覆写的区间均包含零；不能用这个宿主改动解释写入提速。

对默认的读写实现另做两组对照，不开 handoff。下表是每个独立 workload 的中位毫秒和**组内**耗时变化的中位数，不是把两个中位数相除。后两行先预热 4 MiB 文件，再对 1,024 个乱序页分别改写其中 64 或 4,096 字节，**每写随即读回整页**，计入末尾 `fsync`，并检查完整数据。它把干净页淘汰后的重新取页计入成本。

| 非门禁诊断 | #212 | 默认读写改动 | 配对变化 [95% 区间] |
|---|---:|---:|---:|
| 128 次 `lseek` + 标量读 | 3.135 | 1.586 | −49.4% [−49.9%, −49.2%] |
| 128 次八段 `preadv` | 12.170 | 1.692 | −86.1% [−86.2%, −85.8%] |
| 每页改 64 字节再读回 | 78.438 | 56.975 | −27.2% [−28.1%, −26.9%] |
| 每页改 4,096 字节再读回 | 58.075 | 55.152 | −5.1% [−6.1%, −4.0%] |

## 单 vCPU 的共享队列实验

`PVISOR_VM_FS_QUEUE_HANDOFF=1` 允许 guest 与 host worker 在短时间内通过现有共享环交接**已确认**的请求。每端最多检查 512 次；未完成必须重新启用通知、加屏障、复查队列，再交给 IRQ/休眠路径。它不改文件的可见性，不提前回复 `WRITE`，也不免除 `fsync`。[协议、协商与失败实验](native-queue-handoff.md)。

先固定实验 runner `086ad09a9f06`，只切换该开关。这一批使用 #212 的文件 API 和改过的 host RAM 屏障，并不包含上表的散读、seek 和写路径改动。

| #212 原工作负载 | 关 → 开，ms | 配对变化 [95% 区间] | MMIO exits 关 → 开 | 整个 VMM 在线程上实际使用的 CPU-ms 关 → 开 |
|---|---:|---:|---:|---:|
| 顺序热读 | 12.906 → 5.078 | −61.2% [−62.9%, −59.9%] | 1,036 → 237 | 13.04 → 8.61 |
| 乱序热读 | 12.917 → 4.576 | −64.8% [−68.5%, −60.4%] | 1,036 → 236 | 13.05 → 8.54 |
| 顺序写 + sync | 25.602 → 11.485 | −55.9% [−58.2%, −52.9%] | 1,035 → 172 | 25.90 → 12.95 |
| 乱序覆写 + sync | 25.818 → 11.648 | −54.5% [−56.9%, −52.9%] | 1,037 → 194 | 27.26 → 15.09 |

右两列来自**另外 7 组**握手诊断的中位数：KVM vCPU 计数及 `/proc/$pid/task/*/schedstat` 的运行时间总和，含边界握手，不是 CPU 利用率或尾延迟。写负载的 halt exits 分别从 1,026 / 1,023 降到 11 / 10。这是短窗口内连续请求的结果；共享 CPU 掩码既不是核心预留，也不保证有宿主配额。在稀疏请求或主机拥塞时可能白白轮询，因此不更改默认开关。

## 显式发布一个新目录

同一 Rust native runner（handoff 关闭），8 × 512 KiB，4,096 次 1 KiB 写；每次都有新根、VM、文件校验和相同的单目录发布目标。[三臂的边界](../vm/packed-tree.md)不同于普通 `:rw`：最终名字下不显示中间字节。计入试验目录准备、VM 启停和最终 host 完成，**不把 guest 提交标记当作已发布**。

| 方案 | 端到端中位 ms | 相对上一行的配对变化 [95% 区间] |
|---|---:|---:|
| 在共享目录逐次小写后发布 | 223.54 | — |
| guest tmpfs 暂存，分文件批量导出并发布 | 110.90 | −50.8% [−52.2%, −49.6%] |
| guest 暂存后交付定长包，host 导入再发布 | 107.97 | +0.3% [−7.0%, +3.9%] |

**保留分阶段批量写这个方向，不引入通用 pack importer。** 第三臂把一部分工作移出 VM，但增加了 host 对 4 MiB 的又一次读写以及同步；退出后完成阶段的中位数是 11.34 ms。相对直接批量导出，未检出端到端差异。三臂相同的是字节和文件名，不是任意 UID/GID、xattr、hardlink 或崩溃恢复语义。更值得试的是有大量小文件的发布，而不是继续改这八个文件上的格式。

以上时延实验每项 15 个完整随机顺序 block、新 VM、1 vCPU / 256 MiB、宿主 CPU 2–5、btrfs；不清宿主页缓存、不丢慢样本。区间是对组内百分比的中位数作 20,000 次百分位 bootstrap，未作多重比较校正。原始来源在本地 `benchmark/vm/.data/native-post212/`，含每臂命令、哈希、逐操作日志与独立计数。固定探针 SHA-256 `a26febf3addc…`；`host-pairs`、`vector-pairs`、`mixed-pairs` 种子 21213，`handoff-pairs` 21243，`stage-pairs` 21227。未跨机复现；这些工程结果不替代三后端门禁。

## 正确性与复现

`pvisor-kernel/tests/readv.c` 的 `check` 验证跨 iovec EOF、错误后的部分完成、共享文件位置和用户页 fault；`profile` / `profile-seek` 验证计数。`time-scatter` / `time-seek` 计入循环中的数据校验、不等待 profile checkpoint。例：

```sh
cc -static -O2 -Wall -Wextra -Werror pvisor-kernel/tests/readv.c -o "$root/probe"
PVISOR_GUEST_KERNEL=rust-native timeout 30 "$VM" --rootfs "$root" \
  --cpus 1 --memory 256 --task-stdio -- /probe time-scatter /records </dev/null
```

每次使用新的磁盘根和管道形式的 task stdio。[KVM 验收说明](../../pvisor-kernel/README.md#tests-and-hardware-acceptance)涵盖仍打开的 fd 上的 host 重写、增长、截断、rename/recreate，以及读预热后的短写。新的短写探针在 #212 基线应返回 3 字节时实际得到 `EIO`；候选返回 3、下一写返回 `EFBIG`，host 在 `fsync` **之前**已经能读到正确字节，同页相邻的 host 更新不被覆盖。首次映射与写竞争、解除映射后刷脏页、稀疏文件和 EOF 用单独真机用例验证。未证明已映射后整个旧 writeback 路径都能向调用方报告部分字节数。

[完整门禁的复现步骤](../vm/guest.md#本地复现)与[分阶段新树实验](../vm/packed-tree.md)使用不同的时钟和等价条件。不要用单项提速冲抵门禁失败，也不要将仅在新名字发布时才可见的工作流当作普通 `:rw`。
