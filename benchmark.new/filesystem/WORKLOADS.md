# 文件系统负载 V2：机制、资源边界与完整任务

## 结论与状态

**后续文件系统评估改为三层性能图谱：用机制负载解释收益，用资源边界寻找失效点，用完整任务判断产品价值。七工具保留为历史应用回归，不再承担系统性能总分。**

这是一份实验协议，不是性能结果。`workloads_v2_run.py` 已实现全部19个锚点的
guest写回关闭/开启对照，包括静态Rust负载、固定fixture、逐case新VM、分阶段
时钟、guest逐轮校验、host最终状态校验及CSV/SVG/PDF分析。按快速摸底要求，
当前执行profile为每case三对独立环境、内部三轮；实际成功、失败与缺失库存以
各批次`records.json`及分析为准，不从计划数推断已完成测量。

`workloads_v2.py` 保留最初的离线设计快照，其N5计划和
`executor="not_implemented"`描述该离线提案，不是当前执行器的运行状态。
host写缓存、lower读缓存对照及扩展曲线仍未接入新执行器；细粒度压力与队列
插桩仍缺失。旧入口、CSV、曲线与结论独立保留。

本协议登记在 [B-FS-ENG](../../benchmark/README.md#b-fs-eng)，独立计数属于
[B-FS-DIAG](../../benchmark/README.md#b-fs-diag)。历史曲线协议见 [CURVES.md](CURVES.md)。

### 顶层回答什么

每轮首先回答三个问题：哪些完整任务更快；在哪些容量和并发下失效；请求、等待和
资源证据能否解释差异。三项完整任务分别报告，不随意加权相加，也不从流写单点
推导“整体提速”。没有生产权重或代表性运行轨迹时，不定义通用总分。

### 为什么更换七工具主指标

- 工具名不能直接控制请求粒度、访问局部性、文件数、同步边界和并发组织。
- 小工作集与有限写入量无法保证触及缓存容量或产生实际背压。
- Cargo/npm 后两轮复用编译与安装结果，逻辑工作随轮次改变；不能把差异都解释为FS缓存。
- 多项工具依次执行会互相预热；同一文件流写又在七工具累计之外，整体分数难以解释局部收益。

## 动机

需要判断缓存与异步化节省的是协议往返、前台等待、真正完成时间还是资源。
设计同时覆盖可合并与不可合并、重复与首次访问、容量内与容量外的情况。
持续写入、混合访问和并发退化必须与受益点一起展示。

## 实验设计

### 三层与第一轮范围

| 层次 | 核心问题 | 首轮锚点 | 主要输出 |
| --- | --- | ---: | --- |
| 机制 | 哪种访问形状改变了成本？ | 12 | 操作完成时间、有效吞吐、每单位工作请求/协议字节 |
| 资源边界 | 收益能维持到什么容量与并发？ | 4 | 进度曲线、完成吞吐、CPU/内存及背压证据 |
| 完整任务 | 真实步骤串起来是否更快完成？ | 3 | 各工作流独立的工作时间、同步完成时间及Ready |

quick目录共有19个预设锚点；某处理不适用的case明确排除于该处理的采集计划，
但保留在完整catalog中。先按完整family取得结果，不要求测完所有family才分析。
curves配置登记后续单轴扫描，当前离线生成器和执行器均不展开这些扫描。

### 第一层：12个机制锚点

| ID | 负载 | 要区分的成本与必要校验 |
| --- | --- | --- |
| M01 | 正项路径查询 | 名字/目录复用；stat属性和输入身份一致 |
| M02 | 静态缺项路径查询 | 查询缺失与普通命中分开；核对ENOENT与存活sentinel |
| M03 | 目录枚举 | 宽目录/深目录分开，核对完整条目集合 |
| M04 | 顺序读与重开复用 | lower对象与读取字节固定，区分首轮和驻留重读 |
| M05 | 随机读 | 固定seed和逻辑访问序列，不以顺序预读替代随机命中 |
| M06 | 同文件1 KiB连续写 | 大量小写的guest合并和协议往返成本 |
| M07 | 同文件1 MiB连续写 | 已是大请求的负对照，检查复制/调度附加开销 |
| M08 | 4 KiB随机覆盖 | 局部性、脏页合并及写放大，固定覆盖序列 |
| M09 | 小文件write/close | 文件间不可直接合并的代价，核对全部输出与大小 |
| M10 | 每写4 KiB执行fsync | 同步边界限制合批，保留所有屏障及错误 |
| M11 | 前台读＋后台写不同文件 | 测写回对读完成时间的干扰，不把共享inode锁混进此点 |
| M12 | create/write/fsync/close/rename/unlink | 元数据与数据生命周期；rename后、unlink前核对完整字节，最后同步目录并核对缺项 |

每个case规定完整调用序列、逻辑字节/操作数、保留输出和删除集合。
被应用显式删除的数据不算承诺保留字节；不能用逻辑写入量冒充持久化有效吞吐。
同inode多FD、首次copy-up/已copy-up、不同目录/不同挂载另作显式扩展，不隐含混入。
负项查询后的创建/再查询失效验证另列一致性扩展，不偷偷加入M02的纯查询计时；
当前生成器的M02只规定静态缺项和sentinel校验。

当前浅测的M05/M08以固定块置换`(405i+113) mod 1024`覆盖全部4 KiB块，
属于可复现的乱序锚点，不等于独立均匀随机采样；多seed均匀/热点分布留作后续扩展。

### 第二层：4个资源边界锚点

以配置guest RAM为R，扫描 `workers∈{1,4}` × `工作集∈{R/4,5R/4}`。
四点总文件数固定4、请求固定4 KiB、每轮总逻辑写入固定2R、缓冲上限1 MiB。
单worker轮流处理四个文件；四worker各自处理文件，避免同时改变文件数和总写量。
R是配置量，必须同时记录实际guest MemTotal，不能伪称两者严格相等。

该层观察超过缓存容量时的进度、完成吞吐和内存成本，不预先称“已经饱和”或
“达到稳态”。写入总量超过预算不保证队列填满；必须看到实际dirty/writeback、
等待或队列占用证据。扩展时再扫实际压力目标Q的0.25/1/4/16倍突发、固定时长
持续写入和明确标识的慢backing注入，真实设备与人工延迟分开报告。

### 第三层：3个完整任务，独立主指标

| 任务 | 必须覆盖的实际步骤 | 主结果 |
| --- | --- | --- |
| 源码巡检与搜索 | 遍历、git状态、内容搜索、读取匹配文件；固定仓库与输出oracle | 完整任务完成时间 |
| 修改—增量构建—测试 | 每轮执行等量、确定性源码修改，再构建并测试；不测无修改的空构建 | 完整任务完成时间及最终输出同步时间 |
| 离线安装与产物发布 | 从本地固定包展开多文件、生成大/小产物、校验并发布；完整包含流写步骤 | 完整任务完成时间及发布同步完成时间 |

首个可执行fixture将三项任务具体化为：

- S01：真实git仓库含1,024个4 KiB文件；显式遍历及属性检查、`git status`、
  `git grep`、读取全部匹配文件并核对内容与精确结果集，均计入任务时间。
- S02：100个C编译单元，`cc -O0`。Ready后先完整构建、执行并同步，作为单列
  setup；每轮等量修改`unit000.c`、编译该单元、链接全部对象并执行程序核对
  期望输出，再单列修改文件和目录的最终同步。这是固定小型增量构建任务，
  不是整个pVisor或Cargo/npm项目的构建代表。
- S03：Python标准库`tarfile`解包1,024个4 KiB本地文件，再生成128个4 KiB
  文件及32 MiB产物；大产物使用1 KiB连续写。发布前完整字节校验计入工作，
  所有文件和目录同步、原子rename及父目录同步计入最终同步；发布后的再次校验
  单列。每轮保留独立发布目录，不调用公网包仓库。

选定工具的字节摘要、实际argv、fixture摘要与补齐的编译器运行库由批次冻结；
prepared rootfs仍是外部准备目录，未完整复制或证明所有输入均物理不可变。行内
`read_ops`/`write_ops`等是Rust显式操作计数，不包含git、编译器及Python子进程
内部的全部系统调用；不能把这些行字段当作完整协议请求数。

三任务都是预先声明的主要应用结果，不合成一个总分。首轮构建/安装和后续增量
状态明确分开；三轮有相同的任务语义，不以“第二轮什么都没做”模拟缓存收益。
当前N3只给浅度探索、全部配对点和范围，附按环境对重采样的探索性区间；
不能据此宣称稳定确认。如需多个主要任务的同时确认，必须在独立确认批次前固定
多重比较处理，不能从多个未校正区间中挑出一个胜点作为总体结论。
输入内容、依赖、工具版本和网络条件固定。首轮不调用公网registry或真实LLM；
本地包回放不是下载代理、网络offload或完整Agent IOCP的证明。

### 后续曲线：逐轴展开

| 轴 | 预定取点 | 必须固定或注明 |
| --- | --- | --- |
| 元数据规模 | 1K/16K/128K条目；宽度与深度分别变 | 命中/缺项、查询序列与目录布局 |
| 读工作集/R | 0.25/0.5/1/1.25/2 | 顺序与随机分面；首次与重开复用分列 |
| 写请求 | 1/4/16/64/256/1024 KiB | 总逻辑字节、文件数及同步合同 |
| 输出文件数 | 1/4/16/64/256 | 总写量与请求粒度；关闭和目录同步次数保留 |
| 同步间隔 | 每4 KiB/64 KiB/1 MiB及仅最终同步 | 以字节间隔控制，避免改block时顺带改同步频率 |
| worker数 | 1/2/4/8 | 固定总工作；共享inode、不同文件和目录组织分开 |
| 读写混合 | 读比例0/50/90/100% | 固定请求/序列/工作集，共享对象与独立对象分开 |
| 突发量/Q | 0.25/1/4/16 | Q取实际getter/配置观测，不能用名义RAM推算后称实测 |

先逐轴，后补少量有机制依据的交互点；不把所有因素做笛卡尔积。
固定vCPU下增加worker是并发与过度订阅实验，不能称CPU扩展性。
多VM在固定父组资源下的吞吐、公平性和每任务成本属于下一阶段，不能用单VM
四worker代替。开放到达负载还需独立发生器和计划到达时间，当前19锚点不报告
开放负载P99。

### 对照与对象所有权

首轮机制与资源点沿用guest 2 vCPU/512 MiB、父组两核quota/2 GiB、swap=0的
基准预算。应用fixture若需要更大RAM，先单独登记预算profile并显式传入计划，
不能执行时静默扩容；每个对照的两臂保持相同预算，跨预算不合并结果。计划中的
RAM参数不等于实际cgroup已安装，执行器还需记录实际CPU、memory/swap限制。

- guest写回：同一固件和host，仅guest WB 0/1，host WB与DATA均0。
- host异步：guest WB与DATA均0，仅host WB 0/1。
- lower读缓存：guest/host WB均0，仅DATA 0/1；两臂使用同一份物理Immutable lower，
  认证/lease及copy-up语义保持相同。纯写压力不冒充这个处理的适用负载。
- native：同数据、同调用与相同工作量的独立参考，不当成隔离语义等价或单组件消融。

以上列出完整设计的对照边界。当前`workloads_v2_run.py`仅实现guest写回两臂，
其他处理和native仍是后续设计，不能据离线计划中的arm认定已经运行。当前入口
使用SDK VM及相同prepared rootfs/fixture，未接通普通CLI、网络代理或Immutable
lower读缓存的所有权认证实验。

其他实验机制固定，写明实际协商。Mutable与Immutable、lower与upper、首次copy-up
与已copy-up属于独立变量，不能偷偷同时改变。旧/新内核增量另立同WB对照，
不能把WB开启收益归于新补丁。后端横评只比较能满足同一负载/同步合同的模式。

### 缓存状态、独立样本与失败

一个独立环境只执行一个case：`case×condition×pair` 为采样单位，内部三轮。
R1是fresh guest，宿主backing状态另记，不称冷磁盘；R2/R3保留该case状态。
case之间不共用guest数据页或未排空写队列。缓存历史实验必须把历史序列写进
同一个case，不能依赖前一个无关压力case留下的状态。
重开读取还需分列每次pass，不能把首轮中已复用的后续pass一并称为冷访问。

资源case每轮同步后完整读回四个文件；该验证在计时外，但会改变后续轮的页缓存。
因此R2/R3代表“前轮写入、同步、全量验证之后”的明确历史，不是纯写入历史或
重新冷启动。首轮预分配和同步文件亦在setup中，不计入完成吞吐。当前尚无实际
dirty/writeback或队列占用插桩，不从工作集大小单独推断缓存已满或背压拐点。

当前浅度profile为N3配对，seed固定，逐pair随机case及条件顺序；三轮不算N9。
完整19case的两VM臂对应114个计划环境、342条计划轮记录，不是已测库存。
每case先在环境内累加三轮时间，再取三个配对耗时比的中位数，同时保留逐轮
结果、全部三个比值、范围及5000次环境对bootstrap探索性95%区间。
这些区间未校正多重比较；N3也不足以可靠判断分布是否双峰或估计操作尾延迟。
原离线N5方案仍可作为后续探索设计；N30确认须另立独立批次，不混入当前N3。
独立N1计数另跑；先选一对处理，逐family采集，不默认先测完全部后端/消融。

保留所有有效慢值，不设安静期、外部干扰或逐轮全清单门禁。
失败、超时、错误字节和缺项显式报告，不填零、不静默补样；不完整case不计算
其性能提升，已经完整的其他case仍可报告。修复后重建新来源批次，旧失败保留。

### 统一时钟与输出合同

| 字段 | 边界 |
| --- | --- |
| ready | 创建执行器→负载Ready；排除退出 |
| work / API return | 首个任务操作→最后操作返回，包含合同内周期同步；不代表host已接管字节 |
| final sync | 任务结束后的预定文件与目录同步、checked close等收尾；两臂相同 |
| sync completed | 首个任务操作→同步合同完成；作为显式同步写负载的完成吞吐分母 |
| exit | 正常退出与Bundle/错误传播，单独记录；不塞进Ready或工具时间 |

当前SDK入口的Ready在静态payload启动并读取实际guest MemTotal后发出，先于
case setup。工作区准备、线程/缓冲准备、S02首次完整构建等另记`setup_ns`，
不能把Ready解释为应用初始构建已经完成。`work_ns`、`final_sync_ns`和
`completed_ns=work_ns+final_sync_ns`为当前行内的三个主要时钟；验证时间单列，
但S01任务内核对、M12 unlink前校验及S03发布前校验是原任务步骤，仍计入工作。

实际工作流原有的fsync/close必须保留。额外最终同步单列，并同时给出工作开始
至同步完成时间，不能只展示缓存尚未排空的峰值。成功fsync不是掉电恢复验收。
操作延迟分位数必须来自每环境足够多的真实操作样本/有精度说明的直方图，
不能从少量环境均值生成P99，也不能把guest API完成等同于FUSE回复或物理落盘。

guest每轮核对该case规定的字节、名称与结果，host在正常退出后仅检查最终保留
状态。host检查使用独立只读视图，只隐藏经过白名单、空文件与冲突检查的物理
OverlayFS标记；未知标记或与保留输出冲突的whiteout失败。host最终状态校验不
证明R1/R2中间状态独立落盘，也不是掉电恢复测试；S02的程序语义在guest执行
验证，host完整读取最终对象与ELF并检查结构，未进行独立编译结果等价证明。

## 图表与归因

主报告顶部仍按“是否改善→原因和证据→哪些涨跌”输出。当前分析器生成机制
逐轮归一化耗时、资源四点吞吐、资源环境成本、三个工作流逐轮耗时四组SVG/PDF，
每点保留全部三个环境观察。CPU与内存覆盖setup、三轮、验证及退出的整个环境；
内存值是采样的父组`memory.current`峰值，包含既有页缓存影响，不能当作逐任务
精确内存成本或该trial独占增量，也不能代替重置后的`memory.peak`。
下面是扩展后的目标图谱，尚未实现的轴和插桩不能用现有四点替代：

1. 元数据操作率随目录规模变化，附每逻辑操作LOOKUP/GETATTR/物理查询数。
2. 读吞吐随工作集/R变化，区分访问模式与复用轮，附每逻辑GiB的READ及协议字节。
3. 写入返回与同步完成吞吐随block变化，附每GiB WRITE和写放大。
4. 文件数、worker与对象组织曲线，固定总工作，显示全部环境点和退化。
5. 同步间隔曲线，拆工作、最终同步和收尾。
6. 压力过程中的累计进度、内存与等待；缺少host应用前缀插桩时不画虚构的完成前缀。
7. 三个完整任务各自的Ready、工作、同步和退出分布，保留三轮与完整步骤。

已有profile可核对协议调用、WRITE字节/大小桶与background；host队列高水位及
cgroup计量大多是整个owner/环境范围。每case采样窗口、guest dirty/temp页峰值、
压力等待、host应用前缀与guest操作尾延迟需新插桩。缺失为未知，不当作零、精确
命中率、单case资源成本或CPU耗时占比；inclusive span不能相加作为精确归因。
每完成单位的CPU和内存成本，与等待时guest RAM可否卸载分别验证。

## 可执行的计划入口与实施顺序

```sh
python3 benchmark.new/filesystem/workloads_v2.py --profile quick \
  --comparison guest-writeback --output /tmp/filesystem-workloads-v2.json
python3 benchmark.new/filesystem/workloads_v2.py --profile quick \
  --comparison guest-writeback --layer resource
python3 benchmark.new/filesystem/workloads_v2.py --profile curves \
  --comparison lower-read-cache
```

以上旧离线入口只输出设计catalog、适用case、随机采样计划和所需观测，不执行。
其中`executor="not_implemented"`、`performance_samples=false`和
`measured_environments=0`保持原提案语义；它们不是实际采集库存。
`curves`中的轴也只是deferred规范，没有运行时样本。输出拒绝覆盖。
`--layer`可分别计划12个机制、4个资源或3个任务锚点，
并与处理适用性取交集。当前编码7类deferred轴及其子集取点；混合比例、突发量和
上表中更广的网格仍是未编码的扩展蓝图。native参考须显式选择，不混入A/B区间。

当前实际采集入口为：

```sh
python3 benchmark.new/filesystem/workloads_v2_run.py --prepare NEW_BATCH_UNDER_DOT_DATA \
  --rootfs PREPARED_ROOTFS --firmware PREPARED_FIRMWARE \
  --firmware-source FIRMWARE_SOURCE_JSON --samples 3
target/semspec/debug/semspec bench NEW_BATCH_UNDER_DOT_DATA/in.json
python3 benchmark.new/filesystem/workloads_v2_analysis.py NEW_BATCH_UNDER_DOT_DATA
```

准备冻结来源、编译静态payload与SDK driver并生成fixture，在测量外完成；
`--cases M06,M07`可采集明确子集，正式19点省略该选项。计数使用独立新批次的
`--diagnostic --samples 1`，其计数是包含setup、验证和退出的case生命周期范围，
不是逐轮工作阶段计数。分析需要matplotlib才能生成SVG/PDF；`--no-plots`仅生成
CSV/JSON和报告。测量必须经真实`semspec bench`入口，不能把离线计划JSON交给
旧发布器或填进用户表作为新结果。现有`curves.py`、`guest_writeback_curves.py`
和CLI冻结入口不改写；扩展曲线、阶段压力插桩与新对照继续单独实施。

## 方法参考

[fio官方文档](https://fio.readthedocs.io/en/latest/fio_doc.html)分别配置I/O模式、粒度、
工作量、并发与时长，可用于核对数据路径负载参数；它不替代本项目对象所有权和
guest协议计数。[Filebench项目说明](https://github.com/filebench/filebench)提醒按机器
内存调整数据集，不能直接把默认小数据集当成系统容量测试。
[FXMark论文](https://www.usenix.org/conference/atc16/technical-sessions/presentation/min)
将针对文件系统组成部分的微基准与应用负载结合，用于检验可扩展性。
本协议借鉴这些方法，没有宣称已执行这些标准工具或达到论文验收范围。
